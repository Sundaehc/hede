## 一、结论：有缺失，而且其中一条是"正在发生"的回归

不是所有空值都叫问题。本报告把发现分成三类，避免误判：

| 类型 | 含义 | 处理 |
|---|---|---|
| 🔴 **真问题** | 数据本应有、但没写进去，或写进去了但对不上 | 需要修 |
| 🟡 **源头没有** | 字段在代码/界面里存在，但 Excel 源文件从来没有这一列 | 要么补源头，要么从界面隐藏 |
| ⚪ **设计如此** | 空值本身是正常状态 | 不用管 |

**最需要立刻处理的三件事**：

1. **🔴 `jst_monthly_orders.record_key` 自 2026-07-01 起 100% 不再写入**（810,447 行），唯一约束已失效 3 个多月，且**已经产生了 101 组真实重复订单行**。
2. **🔴 `jst_daily_stock`（库存快照）148 天里只有 99 天有数据，缺 49 天** —— 且缺失不集中在周末，是"有人导才有数据"。
3. **🔴 1,390 条进销存明细没有关联到商品身份，其中 917 条的货号明明在档案里**（触发器没解析出来），且 92% 集中在 2026-07 之后。

## 二、🔴 P0-1：`record_key` 停止写入 —— 定位到具体代码行

### 现象

`jst_monthly_orders`（月聚水潭订单，2026 年分区 293 万行）的去重键 `record_key` 按月统计：

| 月份 | 行数 | `record_key` 为 NULL |
|---|---|---|
| 2026-01 | 475,730 | 0 |
| 2026-02 | 289,745 | 0 |
| 2026-03 | 399,347 | 0 |
| 2026-04 | 433,080 | 0 |
| 2026-05 | 526,578 | 7 |
| **2026-06** | 6 | 6 |
| **2026-07** | 219,656 | **219,656（100%）** |
| **2026-08** | 248,996 | **248,996（100%）** |
| **2026-09** | 277,636 | **277,636（100%）** |
| **2026-10** | 64,146 | **64,146（100%）** |

**分界线非常干净：2026-07-01 之前是 0，之后是 100%。**

### 根因：两条导入路径写的列不一样

| 路径 | 文件 | 是否写 `record_key` |
|---|---|---|
| 一次性归档导入脚本 | `backend/scripts/import_jst_monthly_orders_archive.py:156` → `record["record_key"] = _fingerprint(record)` | ✅ 写 |
| **应用内滚动窗口导入（当前在用）** | `backend/storage/vip_repository.py:557` `import_monthly_order()` | ❌ **不写** |

`vip_repository.import_monthly_order()` 在 574–589 行构造的 record 只有 `source_workbook / source_sheet / source_row_number / 映射列 / order_time_at / ship_date_value / raw_payload`，**没有 `record_key`**，然后第 625 行 `self._batch_insert(...)` 直接插入。而 `record_key` 列可空，所以插入静默成功、无任何报错。

### 后果（已经发生，不只是隐患）

- 唯一约束 `uq_jst_monthly_orders_order_time_record_key (order_time_at, record_key)` 对这 81 万行完全失效（PostgreSQL 唯一索引允许多个 NULL）。
- 已检出 **101 组重复**、**103 行多余**，例如：

```
内部订单号 20188301   RCW62308S0101225-230   2026-07-09 17:46:58   数量=1  ×2
内部订单号 20250705   RCW62307S0101245-250   2026-07-18 06:33:06   数量=1  ×2
内部订单号 20254650   RA1361560DA3A3225      2026-07-18 17:59:17   数量=1  ×2
内部订单号 2071402    QBDZP-WZ00101          2026-07-21 07:03:49   数量=1  ×2
```

### 建议

1. 让 `import_monthly_order()` 复用 `_fingerprint()` 计算 `record_key`（把该函数提到共享模块，避免两处实现漂移）。
2. 回填历史 NULL：对 `record_key IS NULL` 的行按同一算法补算（可先补到临时列核对，再落库）。
3. 回填并**去重**后，把 `record_key` 改为 `NOT NULL`，让约束真正生效。
4. 顺带排查：这个滚动窗口导入路径**是否也漏写了其它"派生列"**（它把全部值按 `str(value).strip()` 存，与归档脚本的 `_integer()/_numeric()` 处理不一致）。

## 三、🔴 P0-2：库存快照缺了三分之一的天数

`jst_daily_stock`：15,298,482 行，实际日期范围 **2026-05-14 ~ 2026-10-08**，共 148 天，但**只有 99 天有数据 —— 缺 49 天**。

缺失日按星期分布：周四 11、周六 9、周二 7、周三 7、周五 6、周日 5、周一 4；
有数据日按星期分布：周一 17、周日 16、周五 15、周二 14、周三 14、周六 12、周四 11。

**两边都均匀分布在七个星期几上 → 不是"只在工作日采集"，而是"有人执行导入才有数据"。** 缺失样例：`2026-05-19~24`、`06-18~25`、`07-05~10`、`07-14~16` …

⚠️ 顺带发现一个**数据建模隐患**：`jst_daily_stock.stock_date` 是 **`'MM.DD'` 格式的文本、没有年份**（`10.08`、`09.30`），真实日期在 `stock_date_value`（date 类型）。目前数据只跨 2026 年 5~10 月，所以两者都恰好是 99 个不同值、暂未出错；**一旦跨年，`stock_date` 会把 2027-05-14 和 2026-05-14 合并成同一个值**。建议查询一律改用 `stock_date_value`，并考虑废弃/规范 `stock_date`。

### 关于那 359 行"没有商品编码"的明细 —— 不是导入事故

它们**一一对应 359 张单据**，且凭证类型全部是结算类：

| 凭证类型 | 单据数 |
|---|---|
| 应付款减少 | 299 |
| 应付款增加 | 52 |
| 应收款减少 | 4 |
| 应收款增加 | 4 |

这些行"没有货号、没有数量，但带金额"，是**财务结算凭证**的固有形态，不是空行被误导入。⚠️ 但由此产生一个副作用需要确认：这类单据的 `total_count` 永远是 NULL —— 实测"未删除单据中 `date` 或 `total_count` 为空"的 **300 张，100% 就是结算类凭证**（359 张中 59 张已软删除）。所以这不是数据缺失，是凭证类型的正常表现。

**而 183 张"缺供应商"的未删除单据也基本正常**：101 张报损单 + 80 张报溢单 + 2 张其它 —— 报损/报溢本来就没有供应商。其中**只有 1 张属于进货类**（进货单/进货订单/进货退货单），这一张值得单独看一眼。

**真正需要修的是那 902 张纯数值不符的单据**（勾稽逻辑/重复导入导致）。

**关于 `data_quality_issues` 空表（勘误）**：这是我上一版报告里判断错的一处。读了 `backend/scripts/audit_data_governance.py` 的实现后确认：它的 `ISSUE_SPECS` 校验的是**"原始日期/时间字符串能否解析进对应的 typed 列"**（即原文列有值、但 `*_value` 解析失败的情况），**并不是"缺值"检查**。所以表为空只说明**没有解析失败的日期值**，属于健康结果。该任务 `HedeDataGovernanceAudit` 每天 2:40 运行、Last Result 为 0，与空表完全一致。至 `alimama_creative_daily_quarantine` 的 10,862 行来自阿里妈妈素材采集链路，与治理巡检无关。
