# 采购入库历史与库龄参考

## 数据范围

从 `C:\Users\Administrator\Desktop\采购入库` 导入全部 `.xlsx` 文件，排除 Office 临时文件。不修改原有 `jst_purchase_inbound_daily`、`jst_purchase_inbound_items`、采购单、经营历程和当前库存表，不触发库存增减。

新建的对象：

| 对象 | 用途 |
|---|---|
| `jst_purchase_inbound_history` | 一行对应一条来源入库明细，按 `inbound_date` 年度分区 |
| `jst_purchase_inbound_history_sources` | 文件 SHA-256、导入状态、数量、日期范围和错误记录 |
| `v_jst_purchase_inbound_age_candidates` | 已成功导入、已入库、正数量的采购进仓候选明细 |
| `mv_jst_purchase_inbound_age_reference` | 商品编码 / 款式编号 / 原始货号 / 仓库维度的首入、末入和历史采购数量参考 |

商品编码保留条码粒度；款式编号和原始货号单独保存，避免把二者当成同一个标识。尺码仅从“颜色及规格”的最后一个分号后提取，没有明确分隔符时为空，不猜测条码尾数。所有非空来源列保存在 `raw_payload`，包括图片链接、供应商、退货、质检、备注等。

## 库龄含义

物化视图提供的是**来源覆盖范围内的采购首入天数参考**，不是当前剩余商品的准确实物库龄。`received_quantity` 是历史入库数量，不是当前库存。

源文件里的“采购进仓”可能实际为客退、唯品退供、返修。导入按供应商和备注打上 `customer_return_candidate`、`rework_candidate`、`purchase_candidate`、`other` 标记；前两类默认不进入采购首入参考。它们只是规则候选，不能代替业务审核，不能保证识别全部退货或返修。原始明细仍全部保留，可以重新审核分类。

准确剩余库龄还需要：统一商品 / 颜色 / 尺码映射，确认仓库对应关系，补齐期初库存、采购退货、销售出库、销退、调拨、盘点等完整流水，再按批次实物追踪或明确的先进先出规则分配当前余量。不得直接将首入日期作为所有现存数量的入库日期。

## 跨年性能设计

- 对入库日期做年度范围分区。通过父表查询，不需要按年度手工拼接 SQL。
- 日期条件使用 `inbound_date >= :start_date AND inbound_date < :end_date`，不要在日期列上套 `EXTRACT(YEAR)`、`TO_CHAR`、字符串截取，否则影响分区裁剪和索引。
- 每个分区继承商品编码＋日期、款式编号＋日期、原始货号＋日期、仓库＋日期、采购单号＋日期索引。
- 跨全部年份的商品首入 / 末入查询直接使用物化视图，不重复扫描数百万明细。该视图只能回答整个已导入历史的参考值；任意指定时间段的汇总仍需按日期过滤明细。
- 查询函数 `storage.purchase_inbound_history.query_inbound_history` 强制日期范围并限制最多返回 1,000 条；没有实现深页 `OFFSET` 或默认全表导出。
- 文件通过流式 XML 读取，不依赖这些报表错误的 `dimension=A1`；内存随单行处理，不把整张表读入列表。优先使用环境已有的 `lxml`，没有时使用标准库流式实现。
- PostgreSQL `COPY` 写入临时暂存表，再在同一事务合并；导入成功后更新统计信息，刷新库龄参考。后续刷新使用并发模式，减少影响读查询。

## 执行及恢复

在 `backend` 目录执行：

```powershell
python -m scripts.import_purchase_inbound_history --source-root "C:\Users\Administrator\Desktop\采购入库"
```

只初始化新对象，可执行 `database/purchase-inbound-history-2026-10-27.sql`。对应 Alembic 增量为 `20261027_0079`；不要为此盲目执行整个历史迁移链。年度分区由导入器依据实际日期自动创建。

- 每个文件独立事务，单文件异常整体回滚；之前成功的文件保留。
- 校验和相同的文件再次执行会跳过，不受改名影响；同路径文件内容变化会拒绝直接追加，需审核覆盖规则。
- 尚未完成的文件在进程退出后可用原命令重试，重新读取该文件，不是从中间行续传。导入器数据库锁防止多进程同时导入。
- 校验和只能避免相同文件重复导入。不同导出的文件若覆盖相同业务明细，尚无可靠来源明细 ID 能自动判定是否重复，应先核查，不要把不同文件的所有相同行简单去重，以免误删真实多行。
- 文件运行、成功、失败情况在来源表可查；控制台每 50,000 行输出进度。后台启动时应将标准输出和错误输出写入项目 `backend/logs`。
- 脚本独立运行，不依赖后端服务，也不启动或重启后端。

跨年查询示例：

```sql
SELECT inbound_date, inbound_id, goods_code, warehouse, quantity, receipt_class
FROM public.jst_purchase_inbound_history
WHERE goods_code = '实际商品编码'
  AND inbound_date >= DATE '2024-01-01'
  AND inbound_date < DATE '2027-01-01'
ORDER BY inbound_date DESC
LIMIT 100;

SELECT goods_code, warehouse, first_inbound_date, last_inbound_date,
       CURRENT_DATE - first_inbound_date AS first_receipt_age_days
FROM public.mv_jst_purchase_inbound_age_reference
WHERE goods_code = '实际商品编码';
```

## 每日采购入库导入

- 日任务入口为 `scripts.import_purchase_inbound_daily`，固定读取 `\\Hede\运营组资料\影刀\商品库存\采购入库.xlsx`，不扫描同目录的其他文件。
- 要求文件非空、最后修改日期为中国业务当天，且大小和修改时间稳定后才读取；每条明细的入库日期也必须为当天。这里的“当天”沿用现有业务库的 UTC+8 业务日期，并不是电脑浏览器所在时区。
- 沿用 `run_scheduled_task` 记录执行历史、错误摘要及 `logs/import_purchase_inbound_daily.log`；业务状态以 `import_purchase_inbound_daily` 写入 `scheduled_task_status`。只有明细提交及库龄参考刷新都成功才标记成功。当日成功后后续触发直接跳过，不再读取文件或导入。
- 原历史数据已经覆盖部分当日数据，日任务不能直接追加。仅对来源包含的“入库日期＋入仓单号”执行整单替换，保留文件内真实的多条同商品明细，不按商品或金额简单去重；其他入仓单及更早历史不变。**日文件必须包含其中每张入仓单的全部明细，而不能是按商品筛选的部分明细。** 来源未出现的入仓单不会因为文件缺失而被删除。
- 新来源先完整读取、验证到暂存表，再在单事务里替换和记录完成；读取出错或写入失败会回滚本次明细变更。相同内容通过 SHA-256 跳过；若明细已提交但物化视图刷新失败，下次只跳过已提交文件并补做刷新，不重复追加。
- 原始来源表中的 `imported_rows` 表示该文件当时导入的行数。后续整单覆盖会使旧来源当前仍保留的明细数减少，不能再将全部来源的历史导入行数相加作为当前明细表总数。
- 日任务与桌面历史导入共用 PostgreSQL advisory lock，避免并发覆盖；已被占用、文件不存在、文件过期、不稳定、空表或导入失败均保持可重试，并记录原因。任务独立运行，不依赖后端服务。
- 注册脚本 `scripts/configure_purchase_inbound_daily_task.ps1` 只新增任务，不修改已有任务、不立即导入；需要显式确认调度时区。计划每天 08:05 首次触发，失败每 30 分钟重试，当天成功后跳过。采用与现有网络文件导入相同的已登录账户，注销后不会运行，不能改成没有共享目录权限的 SYSTEM 账户。
