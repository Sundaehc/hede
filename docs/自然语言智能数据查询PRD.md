| 项目 | 内容 |
| --- | --- |
| 产品名称 | 智能数据查询 |
| 所属系统 | 赫德商品运营中台 |
| 文档版本 | V1.0 |
| 状态 | 评审稿 |
| 日期 | 2026-08-16 |
| 产品定位 | 通过自然语言完成跨模块数据检索、统计分析、页面筛选与结果导出 |

## 1. 项目背景

### 1.1 建设背景

现有系统已经沉淀商品信息档案、商品精细表、商品货品表、工厂渠道看板、采购单、经营历程、库存、供应商、仓库和定时任务等数据，但用户仍需要先理解模块位置、字段名称、筛选方式和统计口径，才能获得所需结果。

部分临时分析仍依赖人工组合筛选、导出 Excel 或由开发人员执行 SQL，存在以下问题：

1. 用户寻找数据的路径长，同一个问题可能需要进入多个页面查询。
2. “销量、库存、款号、渠道、传统赛道”等业务词存在固定口径，新用户不易准确使用。
3. 临时查询频繁占用开发人员时间，结果缺少统一的数据截至日期和来源说明。
4. 单独建设聊天页面容易与现有商品详情、筛选、导出和权限体系割裂。

### 1.2 产品目标

1. 用户可以使用自然语言查询已有业务数据，无需编写 SQL 或熟悉数据库表名。
2. 查询结果与现有业务页面联动，可直接进入商品、货品表、精细表、采购单或经营历程继续处理。
3. AI 查询与现有页面使用同一套指标、渠道、日期和权限口径，避免出现两套结果。
4. 每次查询明确展示数据截至日期、统计口径、来源和异常提醒。
5. 将常见临时查询沉淀为可复用、可收藏、可导出的查询视图。

### 1.3 产品原则

1. **查询优先**：首版仅提供只读查询、页面联动和导出，不自动修改商品、库存、采购或财务数据。
2. **复用现有逻辑**：优先调用现有业务接口、仓储层和统一统计服务，不让模型自行重算业务指标。
3. **结果可追溯**：所有结果均包含数据日期、来源、口径及必要的质量提示。
4. **权限一致**：用户在智能查询中可看到的数据不得超过其在现有页面中的权限。
5. **自然语言与结构化筛选互通**：自然语言可生成页面筛选，页面筛选也可作为后续问答上下文。

## 2. 范围说明

### 2.1 首版范围

首版支持以下查询领域：

| 查询领域 | 支持内容 |
| --- | --- |
| 商品档案 | 品牌、货号、原始货号、款号、颜色、年份、季节、供应商、成本、材质、尺码组、图片等 |
| 商品精细表 | 商品基础信息、上下线状态、平台指标、唯品指标、当前及历史日期数据 |
| 商品货品表 | 销量、库存、在途、缺货、补单、尺码明细、平台日/周/月销量、货号明细和款号汇总 |
| 工厂渠道看板 | 工厂款数、销量、传统赛道、直播赛道、清仓销量及占比 |
| 采购单管理 | 采购单、供应商、仓库、交期、数量、金额、完成状态和商品明细 |
| 经营历程 | 进货、退货、调拨、损益、批发销售、应收应付等单据和明细 |
| 基础资料 | 品牌、供应商、仓库、一般客户、科目和尺码组查询 |
| 任务状态 | 定时任务最近执行时间、业务日期、成功/失败状态和错误摘要 |

### 2.2 非目标

1. 首版不允许通过自然语言执行新增、编辑、删除、导入、审批或重跑任务。
2. 不向用户暴露数据库账户或原始 SQL 编辑器；所有部门均可使用任意只读 SQL 查询，但只能访问账户现有权限覆盖的数据。
3. 不替代货品表、精细表等专业大表页面的完整编辑和批量操作能力。
4. 不对商品、工厂或供应商自动作出采购、淘汰等业务决策。
5. 不对缺失数据进行推测填充；无来源的数据必须明确显示为“暂无数据”。

## 3. 用户与权限

| 用户角色 | 典型需求 | 可用范围 |
| --- | --- | --- |
| 超级管理员 | 跨模块核数、任务状态、数据质量排查 | 按超级管理员现有权限访问全部已开放查询 |
| 商品部/开发部 | 商品资料、工厂、库存、销量、采购分析 | 商品档案、货品表、精细表、工厂看板、采购单及已授权基础资料 |
| 运营部 | 平台销量、库存、上下线、商品经营表现 | 已授权品牌的商品、精细表、货品表和工厂渠道数据 |
| 采购/供应链 | 采购单、交期、供应商、进货和库存 | 采购、进销存及已授权商品资料 |
| 财务部 | 单据金额、供应商、一般客户、应收应付和科目 | 财务及进销存授权范围；商品敏感字段按现有权限控制 |
| 普通查看人员 | 简单商品或业务查询 | 仅限原有查看权限，不因使用智能查询扩大权限 |

### 3.1 权限规则

1. 智能查询入口是否可见由新增权限 `ai_query.view` 控制。
2. 查询商品、货品表、精细表、采购单、进销存等数据时，继续校验对应模块权限。
3. 成本、采购价、金额、供应商联系方式、操作日志等敏感字段按字段权限返回。
4. 品牌权限、部门权限和数据范围必须在后端执行，不能只依赖前端隐藏。
5. 普通账户不得通过智能查询看到超级管理员操作日志。
6. 无权限字段不进入模型上下文；返回时提示“当前账户无该字段查看权限”，不得以空值伪装。

## 4. 信息架构

### 4.1 页面入口

系统采用“独立页面 + 业务页面上下文入口”的双入口设计：

```text
左侧导航
  └── 智能查询
        ├── 新建查询
        ├── 查询历史
        ├── 我的收藏
        └── 已保存视图

现有业务页面
  ├── 商品信息档案 ── 问当前商品/当前筛选
  ├── 商品精细表 ──── 问当前日期/品牌/筛选
  ├── 商品货品表 ──── 问当前货号/款号/库存销量
  ├── 工厂渠道看板 ── 问当前工厂/年份/赛道
  ├── 采购单管理 ──── 问当前单据/供应商/交期
  └── 经营历程 ────── 问当前单据/仓库/客户
```

### 4.2 独立智能查询页

独立页面用于跨模块查询和连续追问，包含：

1. 自然语言输入区。
2. 推荐问题和最近查询。
3. 查询条件确认区。
4. 结论、指标卡、表格或图表结果区。
5. 数据来源、数据截至日期、口径和质量提示区。
6. 应用到现有页面、查看详情、导出、收藏和反馈操作。

### 4.3 业务页面上下文入口

1. 在现有页面工具栏提供“问数据”入口，使用图标和文字按钮，并提供悬停说明。
2. 打开后自动携带当前模块、品牌、日期、筛选、视图、当前行或已选商品。
3. 用户可直接提问“这双鞋”“这些商品”“当前工厂”，无需重复输入上下文。
4. 用户可以查看并移除系统携带的上下文，避免误用隐藏条件。
5. 关闭查询面板后不改变原页面状态；只有点击“应用筛选”才更新页面。

## 5. 核心用户流程

### 5.1 从自然语言查询到业务页面

```text
用户输入问题
  → 识别查询领域、指标、维度、日期、品牌和筛选条件
  → 需要时进行一次澄清
  → 展示结构化查询条件
  → 执行受控只读查询
  → 返回结论、数据表、来源和数据日期
  → 用户查看详情 / 应用到页面 / 导出 / 收藏
```

示例：用户输入“查询千百度男鞋近 7 天无销量、整体库存大于 50 的商品”。系统返回商品数和明细，并提供“在货品表中查看”。点击后打开千百度男鞋货品表，自动应用“近 7 天销量 = 0、整体库存 > 50”的筛选。

### 5.2 从业务页面发起查询

示例：用户在商品货品表打开货号 `QC153883D54` 的详情，点击“问数据”并输入“近 30 天各平台销量趋势”。系统自动携带品牌、货号和当前业务日期，返回趋势图及平台明细，不要求用户重新输入货号。

### 5.3 连续追问

同一会话内保留已经确认的品牌、货号、日期范围和统计粒度。用户可以继续输入：

1. “只看得物。”
2. “和上一个 30 天比较。”
3. “按尺码展开。”
4. “导出这些商品。”

新的明确条件覆盖旧条件；系统每次都展示当前生效条件，避免上下文不可见。

## 6. 功能需求

### 6.1 自然语言输入

1. 支持中文业务问题，兼容货号、款号、单据编号、工厂名称、仓库名称和平台名称混合输入。
2. 支持粘贴多个货号，兼容逗号、空格和换行分隔。
3. 支持“今天、昨天、上周、近 7 天、本月、去年同期”等相对日期。
4. 输入时可提示已识别的货号、品牌、工厂、供应商和仓库候选项。
5. 支持停止正在执行的查询和重新生成查询结果。
6. 输入框以自然语言为主，授权账户的查询由 AI 转换为只读 SQL 后执行。

### 6.2 意图识别与查询计划

系统将问题转换为结构化查询计划，至少包含：

| 字段 | 说明 |
| --- | --- |
| `domain` | 商品档案、精细表、货品表、工厂看板、采购、进销存、任务等 |
| `metrics` | 销量、库存、金额、款数、退货率等指标 |
| `dimensions` | 货号、款号、工厂、平台、尺码、日期等分组维度 |
| `filters` | 品牌、日期、平台、状态、数值范围等条件 |
| `grain` | 货号、款号、尺码、单据、日、周、月等结果粒度 |
| `sort` | 排序字段和方向 |
| `limit` | 返回行数上限 |
| `output` | 摘要、表格、趋势图或分布图 |

执行前必须验证字段、指标、关联关系、权限、日期范围和行数限制。

### 6.3 澄清机制

以下情况必须向用户澄清，不能自行猜测：

1. 货号在多个品牌中存在且用户未指定品牌。
2. “销量差、库存高、异常”等词没有明确阈值或比较口径。
3. 用户要求“最近”但当前业务需要明确 7 天、14 天或 30 天。
4. 用户同时要求货号明细和款号汇总但未说明粒度。
5. 请求涉及无权限字段或不可执行的写操作。

可以从现有上下文唯一确定的条件不重复询问。

### 6.4 结果展示

每次成功查询固定展示以下内容：

1. 结论摘要：用一至三句话说明核心结果。
2. 当前条件：品牌、日期范围、平台、粒度、筛选和排序。
3. 数据结果：指标卡、表格或必要的趋势/分布图。
4. 数据截至：显示销售、库存、快照等关键来源各自的最新业务日期。
5. 统计口径：说明销量、库存、渠道和去重规则。
6. 数据来源：展示业务来源名称；详细表名仅在有权限的诊断视图中展示。
7. 异常提示：数据未更新、字段为空、渠道未映射、历史快照缺失等。
8. 后续操作：查看详情、应用到页面、导出、收藏、反馈。

### 6.5 表格与图表

1. 明细和多维汇总默认使用表格，支持排序、分页和列宽调整。
2. 时间序列默认使用折线图；占比使用条形图或堆叠条形图。
3. 图表和表格共用同一份结果，切换展示方式不得重新改变统计口径。
4. 表格中的货号、款号、单据编号、供应商和仓库支持点击进入对应详情。
5. 空值显示“暂无数据”，数据源明确为零时显示 `0`。
6. 默认明细最多展示 200 行；超过上限先返回汇总，并提供异步导出。

### 6.6 与现有页面联动

| 查询结果 | 联动目标 | 联动行为 |
| --- | --- | --- |
| 商品基础资料 | 商品信息档案 | 打开对应品牌和商品详情 |
| 商品经营指标 | 商品精细表 | 带入品牌、日期、货号及字段筛选 |
| 销量/库存/缺货结果 | 商品货品表 | 带入品牌、日期、货号/款号、平台和数值筛选 |
| 工厂渠道结果 | 工厂渠道看板 | 带入品牌、销售年份、日期和工厂筛选 |
| 采购单结果 | 采购单管理 | 打开单据详情或带入供应商、日期、状态筛选 |
| 进销存结果 | 经营历程 | 打开单据详情或带入仓库、客户、单据类型筛选 |
| 定时任务结果 | 系统任务状态 | 定位任务及业务日期，不自动触发重跑 |

页面联动使用标准化 URL 查询参数或共享筛选状态，刷新和复制链接后仍能还原条件。

### 6.7 查询历史、收藏与保存视图

1. 保存用户的问题、结构化条件、结果摘要、数据日期和执行状态。
2. 查询历史默认仅本人可见；超级管理员不能默认查看用户完整结果数据。
3. 用户可收藏高频问题并设置名称，如“男鞋高库存无销量”。
4. 保存视图保存查询条件和展示配置，不固化旧数据；再次打开时按最新数据重新执行。
5. 用户可以删除自己的查询历史和收藏。

### 6.8 导出

1. 支持按当前查询条件导出完整授权结果，而不是只导出屏幕前 200 行。
2. 导出文件包含“查询条件”“数据截至”“统计口径”和“数据明细”工作表。
3. 大结果使用异步导出，页面展示准备进度和完成状态。
4. 导出继续执行字段权限和品牌权限校验。
5. 导出动作写入操作日志，记录查询任务编号、条件摘要和导出行数。

### 6.9 用户反馈

1. 每个结果提供“结果正确/结果有误”反馈。
2. 结果有误时允许选择：数据不全、口径不对、筛选不对、权限问题、展示问题。
3. 反馈关联原问题、查询计划、数据日期和工具调用，不要求用户再次描述全部上下文。
4. 反馈仅用于改进查询规则，不自动修改业务数据。

## 7. 数据口径与来源

### 7.1 数据源原则

1. 商品、销量、库存、采购和进销存查询优先复用现有业务接口或统一查询服务。
2. 所有部门都可以使用 AI 生成的只读 SQL；系统按当前账户的商品、精细表、采购和进销存权限裁剪可见表结构并校验实际引用表。
3. 禁止模型访问账户、会话、角色、操作日志、系统表、文件系统及数据库元数据。
4. 详细数据源、字段定义和查询限制以 [Codex 数据查询说明](Codex数据查询说明.md) 和 [数据库表目录](数据库表目录-2026-08-03.md) 为准。
5. AI 只能看到规范化统一视图和仍在使用的业务表；年度分表、统一父表、底层快照载荷表及已有规范化视图替代的原始表不进入模型结构。

### 7.2 核心口径

| 业务词 | 统一规则 |
| --- | --- |
| 商品货号 | 优先使用商品档案 `sku`；销售明细带尺码编码时按已维护条码构成规则解析 |
| 款号汇总 | 使用原始货号/款号并去除颜色部分，同款不同颜色聚合 |
| 唯品销量 | 使用唯品日销来源；与聚水潭识别为唯品的记录去重 |
| 其他平台销量 | 使用聚水潭日销并按店铺渠道映射和渠道规则归类 |
| 传统赛道 | 直播赛道和清仓之外的销量 |
| 渠道优先级 | 清仓优先于直播，直播优先于传统，单条销量不得重复计入 |
| 在仓库存 | `actual_stock_qty + purchase_warehouse_stock_qty`，组成列按既有逻辑先将空值作为 0 参与公式 |
| 在途库存 | `purchase_in_transit_qty + transfer_in_transit_qty + return_in_transit_qty`，组成列按既有逻辑先将空值作为 0 参与公式 |
| 历史数据 | 优先使用对应日期快照或年度历史表；不存在时明确提示，不使用当前值冒充历史值 |
| 空值 | “暂无数据”不等于 `0`；只有来源明确记录为零时才返回零 |

### 7.4 SQL 业务语义校验

1. 聚水潭销量必须使用净销量字段；唯品销量使用唯品日销销量字段。
2. 平台查询必须优先关联店铺渠道映射；聚水潭和唯品合并时必须排除聚水潭中的重复唯品记录。
3. 历史销量、当前逐日销量和预计算周期销量只能按不重叠口径选用，不能重复相加。
4. 当前库存必须限定最新同步日期；当前库存和历史快照只能分别查询或比较。
5. 商品档案、单据必须过滤逻辑删除记录；精细表历史必须限定品牌和快照日期。
6. 首次 SQL 未通过只读、权限或业务语义校验时，系统将错误原因反馈给模型自动纠正一次；再次失败才结束查询。

### 7.3 时间口径

1. “今天/昨天”优先按业务数据日期解释，并同时显示自然日期与最新业务日期差异。
2. “近 7 天”包含结束日期在内的连续 7 个自然日。
3. 周、月、年度口径复用现有货品表和看板规则，不在智能查询中单独定义。
4. 多个来源最新日期不一致时分别展示，不使用一个日期代表全部来源。
5. 查询历史快照时，商品资料与经营指标的日期归属必须在结果中说明。

## 8. 查询安全与执行机制

### 8.1 受控查询架构

```text
用户问题
  → 权限上下文
  → 业务词典与指标目录
  → 结构化查询计划
  → 查询计划校验器
  → 受控业务查询工具/参数化模板
  → 结果校验与脱敏
  → 页面展示、联动或导出
```

### 8.2 安全规则

1. 查询执行账户使用 PostgreSQL 只读角色。
2. 仅开放白名单业务工具、视图、字段和关联关系。
3. 禁止 `INSERT`、`UPDATE`、`DELETE`、DDL、多语句执行和数据库文件读写。
4. 模型输出必须通过 PostgreSQL 语法树、表白名单和危险节点校验，并在只读事务中执行。
5. 模型输出还必须通过销量、渠道、日期、库存、历史快照、逻辑删除和空值等业务语义校验。
6. 强制执行行数、日期范围、超时和并发限制。
7. 查询前后均执行权限校验，防止缓存或导出绕过权限。
8. 模型只接收完成字段过滤后的结果，不接收用户无权查看的数据。
9. 查询失败不得回显数据库连接信息或内部堆栈；成功查询可以向授权用户展示实际执行 SQL 以便核对口径。

### 8.3 查询工具建议

首版提供以下后端受控能力：

| 工具 | 用途 |
| --- | --- |
| `query_product_archive` | 商品基础资料、材质、成本、供应商、尺码组等 |
| `query_fine_table` | 当前/历史精细表指标和唯品指标 |
| `query_product_goods` | 货号明细、款号汇总、库存、销量、在途和补单 |
| `query_sales_summary` | 按品牌、货号、平台、工厂和时间汇总销量 |
| `query_inventory_summary` | 当前或快照库存、在途、缺货及尺码明细 |
| `query_factory_channel_dashboard` | 工厂传统、直播、清仓销量和占比 |
| `query_purchase_orders` | 采购单及明细查询 |
| `query_inventory_documents` | 经营历程单据及明细查询 |
| `query_master_data` | 品牌、供应商、仓库、客户、科目和尺码组查询 |
| `query_task_status` | 定时任务状态和错误摘要查询 |
| `export_query_result` | 导出已授权查询任务结果 |

每个工具统一返回 `data_as_of`、`source_names`、`metric_definition`、`warnings`、`row_count` 和可跳转页面参数。

## 9. 异常与边界处理

| 场景 | 处理方式 |
| --- | --- |
| 查询条件不完整 | 提出一个最关键的澄清问题，并保留已识别条件 |
| 无匹配数据 | 展示已执行条件、数据日期和可能原因，不编造结果 |
| 最新来源未更新 | 返回最近可用业务日并明确提示延迟 |
| 历史快照不存在 | 列出最近可用日期并允许用户选择 |
| 渠道无法映射 | 归入“其他/待维护映射”并展示警告，不擅自归类 |
| 用户请求写操作 | 明确首版仅支持查询，并提供跳转到有权限的现有编辑页面 |
| 查询结果过大 | 先返回汇总或 Top N，完整结果转异步导出 |
| 查询超时 | 保留原条件，提示缩小日期或维度，并支持重试 |
| 无字段权限 | 明确提示权限不足，其余有权限字段继续返回 |
| 来源口径冲突 | 停止合并冲突指标，分别返回来源结果并提示维护口径 |

## 10. 性能与体验要求

| 类型 | 目标 |
| --- | --- |
| 意图识别与查询计划 | P95 不高于 2 秒 |
| 常规商品/单据查询 | P95 不高于 3 秒 |
| 跨来源聚合查询 | P95 不高于 8 秒 |
| 缓存命中查询 | P95 不高于 500 毫秒 |
| 页面应用筛选 | 交互反馈不高于 300 毫秒 |
| 首屏稳定性 | 加载过程保留稳定高度，不出现明显页面抖动 |
| 查询并发 | 同一用户最多 2 个执行中查询，新的重复查询复用原任务 |
| 明细展示 | 默认最多 200 行，服务端分页 |
| SQL/工具超时 | 常规查询 15 秒；超时后终止执行 |

其他要求：

1. 查询中展示明确的执行状态，不循环显示无意义文案。
2. 用户可以取消长查询，取消后立即释放执行资源。
3. 相同用户、权限、查询计划和数据版本可使用短时缓存。
4. 数据导入完成后通过数据版本使相关缓存失效。
5. 图表、表格、侧栏和弹窗不得遮挡现有页面操作区域。

## 11. 操作日志与可观测性

### 11.1 用户审计

记录以下内容：

1. 查询人、部门、时间和会话编号。
2. 原始问题摘要和结构化查询条件。
3. 调用的受控查询工具、数据日期、执行耗时和返回行数。
4. 查询成功、失败、取消、导出和页面跳转状态。
5. 权限拒绝和敏感字段过滤情况。

操作日志不保存大批量结果明细，不记录数据库密码、连接地址或模型内部推理内容。

### 11.2 运行监控

后台应监控：查询成功率、P50/P95 耗时、超时率、无结果率、澄清率、缓存命中率、导出成功率、用户反馈正确率及各查询工具错误率。

## 12. 数据对象

建议新增以下逻辑数据对象，具体物理表在技术方案中确定：

| 对象 | 作用 |
| --- | --- |
| AI 查询会话 | 保存用户、标题、上下文模块和最近使用时间 |
| AI 查询消息 | 保存用户问题、结果摘要、状态和顺序 |
| AI 查询任务 | 保存结构化计划、权限快照、执行状态、数据版本和耗时 |
| AI 查询结果引用 | 保存短期结果位置、字段定义、行数和过期时间，不长期复制业务明细 |
| AI 查询收藏 | 保存用户命名的查询条件和展示方式 |
| AI 查询反馈 | 保存正确性反馈、问题类型和关联任务 |

查询结果明细原则上不永久复制到新表；需要导出时使用短期结果或按原查询计划重新校验并执行。

## 13. 产品指标

上线后重点观察：

1. 智能查询周活跃用户数和人均查询次数。
2. 无需开发人员介入即可完成的查询占比。
3. 查询成功率、正确反馈率和首次查询解决率。
4. 查询后进入业务页面、导出或保存视图的转化率。
5. 用户平均获得结果时间相对手工筛选/导出的降低比例。
6. 因口径、权限或数据延迟产生的错误反馈数量。

## 14. 验收标准

### 14.1 功能验收

1. 用户可从左侧智能查询页输入自然语言并获得结构化结果。
2. 商品信息档案、精细表、货品表、工厂渠道看板、采购单和经营历程可携带上下文发起查询。
3. 支持按货号、款号、品牌、工厂、平台、仓库、供应商、日期和单据编号查询。
4. 结果可跳转至对应业务页面并正确还原筛选条件。
5. 支持连续追问、查询历史、收藏和按授权导出。
6. 结果固定显示数据截至日期、查询条件、统计口径和异常提示。

### 14.2 数据验收

1. 同一筛选条件下，智能查询结果与对应现有页面结果一致。
2. 唯品与聚水潭销量去重、渠道归类、传统/直播/清仓口径与现有系统一致。
3. 货号明细和款号汇总粒度明确，不发生重复累计。
4. 历史查询只使用对应日期快照或历史来源，不混入当前库存。
5. 空值、零值和无权限字段能够准确区分。

### 14.3 安全验收

1. 无模块权限的用户不能通过自然语言获取对应数据。
2. 用户不能通过提示词要求系统执行写 SQL、绕过品牌权限或返回敏感字段。
3. 缓存、查询历史和导出均不能造成跨用户或跨权限数据泄漏。
4. 所有查询和导出都有审计记录；普通账户看不到超级管理员操作。
5. 数据库只读角色无法执行任何写入和结构变更。

### 14.4 性能验收

1. 常规货号、单据和商品查询满足 3 秒目标。
2. 跨来源聚合查询满足 8 秒目标，超过时可取消或转异步任务。
3. 大结果不阻塞页面，表格使用服务端分页，完整结果可异步导出。
4. 打开查询面板、切换业务页面和应用筛选时无明显页面抖动。

## 15. 迭代计划

### P0：受控查询闭环

1. 独立智能查询页面。
2. 商品档案、货品表、精细表、工厂渠道、采购单、经营历程和任务状态查询工具。
3. 权限校验、数据口径、查询计划校验、结果来源和操作日志。
4. 表格结果、页面跳转、应用筛选和 Excel 导出。
5. 高频问题模板和基础连续追问。

### P1：上下文与复用

1. 各业务页面“问数据”上下文入口。
2. 查询历史、收藏、保存视图和共享授权视图。
3. 趋势图、占比图和查询结果对比。
4. 数据质量提示及未映射渠道、缺失档案的处理入口。

### P2：主动分析

1. 用户订阅查询，按日/周生成结果提醒。
2. 销量异常、库存风险、采购交期和任务失败的主动提示。
3. 在用户确认并具备权限的前提下，跳转现有页面生成待编辑草稿；仍不由 AI 直接写入核心业务数据。

## 16. 待评审事项

1. 首批开放部门和品牌范围。
2. 成本、采购价、金额等敏感字段的具体字段权限。
3. 智能查询入口放置在左侧一级导航还是系统首页顶部全局区域。
4. 查询历史保留期限和用户删除策略。
5. 首版使用的模型、部署方式、并发预算和单次查询成本上限。
6. 保存视图是否允许跨用户共享，以及共享后的数据权限重新校验方式。
