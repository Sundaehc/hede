# 赫德项目开发规则与 UI 规范

版本：1.0  
整理日期：2026-11-05  
适用范围：商品信息档案、商品货品表、精细表、经营历程、采购单、仓库、基础档案、定时任务及系统管理。

本文依据当前仓库代码、配置及已确认的业务要求整理，供开发、评审、测试和交付使用。本文档本身不会改变程序行为；源码修改需要按部署方式发布后生效。

## 1. 使用原则与约束优先级

- **必须**：新增功能和涉及该部分的修改应满足的要求。
- **建议**：默认采用的方案；存在业务或性能理由时可以调整，并说明原因。
- **现状**：当前实现，不代表其他模块已经全部具备相同能力。
- **待完善**：已发现的差异，不应在需求或验收中表述为已完成。

规则发生冲突时，以最新确认的业务需求为准；实际运行状态需结合部署版本、配置和数据核对。历史文档只作背景，不应覆盖已确认的新要求。规则改变时，同步更新相关文档、接口与验证用例。

当前项目协作约束：

1. 后端由项目负责人手动启动。未另行授权，不自动启动、停止或重启后端。
2. `backend/tests/` 不提交、不上传。可以读取和运行现有测试；本轮新增后端验证文件放在已忽略的 `outputs/logs/`，临时数据库也放入忽略目录。
3. `.gitignore` 的历史例外不代表允许上传 `backend/tests/`；提交前以本条要求检查最终文件清单。
4. 保留工作区中已有修改，不为完成当前需求覆盖无关代码；未要求时不自动提交、推送或改写 Git 历史。
5. 文档、代码示例及日志不得包含真实密码、连接串、Cookie、Token、私钥或完整敏感业务数据。

## 2. 技术基线与目录职责

### 2.1 技术栈

以下版本来自当前项目配置；依赖升级以实际依赖文件和锁文件为准。

| 层级 | 当前基线 | 主要约束 |
|---|---|---|
| 前端框架 | Next.js 16.1.7、React 19.2 | 使用 App Router，交互组件按需声明 `use client` |
| 前端语言 | TypeScript 5.9，`strict: true` | 接口、表单、状态必须有明确类型 |
| 样式 | Tailwind CSS 4.2、CSS 变量 | 复用主题和全局页面样式 |
| 组件 | 项目内 shadcn 风格组件、Radix UI、Lucide | 以仓库中的组件实现为准，部分组件已定制 |
| 后端 | Python 3.13+、FastAPI | 请求校验、权限控制、统一业务错误 |
| 数据访问 | SQLAlchemy 2、psycopg、PostgreSQL | 参数化查询、事务、数据库内聚合 |
| 表格处理 | openpyxl、xlrd | 兼容实际模板，保留货号和来源信息 |
| 验证 | pytest；Vitest、Testing Library、jsdom | 优先验证业务行为和回归风险 |

前端开发端口为 `3001`；API 默认端口为 `8137`。前端通过 `/api/*` 代理到后端；覆盖地址使用 `BACKEND_URL`。不要沿用旧说明中的 `3000`。

### 2.2 文件应放在哪里

| 目录或文件 | 职责 |

| `frontend/components/inventory-admin/` | 经营历程、采购、库存及相关业务组件 |
| `frontend/lib/api.ts` | API 调用、请求参数与接口错误处理 |

| `frontend/lib/session-*.tsx` | 查询会话、页面状态和滚动恢复 |
| `backend/api/` | 路由、输入校验、权限、操作日志、响应和后台任务编排 |
| `backend/domain/` | 表结构、字段、品牌、单据类型及业务数值规则 |
| `backend/storage/` | 查询、持久化、事务、批量处理和数据库汇总 |

新增逻辑优先扩展相应层已有能力。前端不直接访问数据库；数据库查询不散落在组件中。已有路由中存在较大的历史业务实现，修改时控制范围，新增共享规则应提取为可复用函数。

## 3. 开发与代码组织规则

### 3.1 命名、格式与类型

- Python 模块、函数和字段使用 `snake_case`；类使用 `PascalCase`；常量使用大写下划线。
- React 组件和类型使用 `PascalCase`；函数和局部变量使用 `camelCase`；前端文件沿用目录中现有的短横线命名。
- 数据库和 API 字段沿用 `snake_case`，页面内部参数按现有 API 封装转换，不随意改变对外字段名称。
- TypeScript 使用明确的请求、响应、表单类型；避免用 `any` 绕过类型检查。未经确认的外部数据用 `unknown` 并检查。
- 前端格式以 `.prettierrc` 为准：2 空格、双引号、无分号、LF、打印宽度 80；Tailwind 类排序由现有插件处理。
- Python 使用清晰的类型标注和小范围辅助函数；当前项目没有统一配置的 Python 格式化门禁，不宣称某个未配置工具是强制检查。
- 不对无关大文件做整文件格式化，不夹带无关重构或依赖升级。

### 3.2 字段和品牌扩展

新增业务字段时，检查完整链路：

`来源表头 → 规范字段 → 数据库列 → 导入映射 → API → 类型 → 表单/详情/列表 → 查询/导出`

字段标签和分组优先维护在已有定义文件，避免多个页面自行维护不同名称。保留 `source_workbook`、`source_sheet`、`source_row_number`、`raw_payload` 等来源追踪信息。

品牌必须使用配置中的编码和档案表。当前既有内置品牌，也支持运行中配置的新品牌；不得只按早期四个品牌硬编码。`all` 是查询范围，不是可写入商品所属品牌。

同货号跨品牌出现时，必须按品牌隔离查询与写入。品牌推断复用现有规则：可信的往来单位或仓库档案优先，客户端品牌只在约定情况下作为备用。不得用客户端旧品牌覆盖单据能够确定的品牌，也不得任意截取货号冒充匹配。

### 3.3 API 与权限

1. API 调用统一放入现有客户端封装；保留登录凭据、`ApiError` 和服务端 `detail` 信息处理。
2. 新接口必须核对后端权限映射与必要的路由内校验。前端隐藏按钮只改善体验，不能代替服务端鉴权。
3. 成本、用户管理、任务管理等敏感能力，同时检查页面访问、接口读取、接口写入和导出权限。
4. 当前账户身份从服务端登录上下文读取，不相信表单传入的账户名或角色。
5. 日期格式错误、起止倒置、超限数值、未知选项等在写入前拒绝；错误应说明业务原因和处理方式。
6. 保持现有接口兼容性。变更参数、响应、分页或空值语义时，联动前端类型、调用方和验证用例。
7. 操作日志记录操作者、模块、动作、目标及必要变化；不记录密码等敏感字段。业务已成功提交时，日志失败不得把成功操作误报为未导入。

### 3.4 前端请求与状态

- 区分**正在编辑的筛选条件**与**已经提交的查询条件**。列表、合计、分页、导出和跨页勾选必须使用同一份已提交条件。
- 页面查询条件变化、切换记录、离开页面时，取消旧请求或使用请求版本判断，防止迟到响应覆盖新结果。
- 并行发起互不依赖的请求；不因为组件重渲染重复请求相同数据。Effect 依赖保持稳定。
- 可以直接从状态计算的值，不另存一份容易失步的状态；确需缓存时，明确缓存键和失效条件。
- 会话状态按账户和页面隔离，复用 `useSessionQueryState`；不把未保存单据、弹窗草稿、敏感业务结果长期写入 `localStorage`。
- 当前页面内跳转、前进/后退保留查询及滚动位置；浏览器刷新清除这些页面状态并回到默认条件；退出登录清理账户状态。以 `session-page-state.tsx` 的边界处理为准。
- 网络中断、权限失败和没有数据是不同状态，不能都显示“暂无数据”。

## 4. 数据正确性与统计规则

### 4.1 来源、空值与数值

- 每个统计明确：数据源、时间字段、品牌、仓库、单据类型、完成状态、删除状态和单位。
- 商品档案、聚水潭库存快照、经营历程库存、采购入库历史属于不同数据集，不直接混用或互相冒充。
- `null`、空字符串和 `0` 必须按业务含义处理。未知值显示“—”，确实为零显示 `0`；不得用 `value || "—"` 隐藏合法数字零。
- 原始货号、商品编码、条码按文本处理，保留前导零；不自动跨颜色、跨品牌补值。
- 金额及业务数量的后端计算使用 `Decimal`；精度遵循具体表和领域配置。经营历程数值配置为 `Numeric(18, 2)`，输入需检查有限数、范围和舍入边界。
- 主单据的数量、金额由实际明细汇总，明细增删改和重新导入后同步更新，不接受客户端合计作为唯一依据。

商品信息档案成本价变化为有效正数时，自动补齐同品牌、同商品档案关联的进货单与进货退货单中空值或零值单价；保留其他已有单价，排除已删除商品、已删除单据和其他单据类型。手工编辑、Excel 导入、定时同步通过数据库触发器共用此规则。补价、明细金额及单据总金额重算在同一事务完成，进货退货单总金额保持负数；自动补价记录经营历程操作日志。完成状态继续按整张单据明细实时判断，不另设“强制完成”标记；仍有缺价明细则保持未完成，全部补齐后按原单据日期参与库存统计。价格未变化或没有有效正成本时不补价，部署本身不批量回填旧单据。

### 4.2 仓库库存的统一口径

当前仓库统计读取经营历程主单据及其商品明细，按单据业务日期统计，不按导入时间统计。优先使用 `date_value`，兼容回退字段 `date`。有日期范围时，开始日和结束日均包含在期间内。

| 指标 | 定义 |
|---|---|
| 期初库存 | 开始日期之前的有效入库量减有效出库量；未指定开始日时为 0 |
| 本期入库 | 期间内有效入库明细数量之和 |
| 本期出库 | 期间内有效出库明细数量之和 |
| 期末库存 | 期初库存 + 本期入库 − 本期出库 |

当前参与方向计算的单据：

| 单据类型 | 库存方向 |
|---|---|
| 进货单、报溢单、批发销售退货单 | 单据仓库入库 |
| 进货退货单、报损单、批发销售单 | 单据仓库出库 |
| 同价调拨单 | 出货仓库出库、入货仓库入库 |
| 进货订单、应收应付类单据 | 不计实物库存 |

必须满足：

1. 排除已删除、未完成单据；完成判断复用 `_record_completion_condition`，与经营历程完成状态一致，不另写一套简化规则。
2. 当前完成规则包含内销客户、总部采购等既有例外，不能只按某一条明细的单价判断整张单据。
3. 调拨两端必须对称处理；同仓调拨净变动为 0。仓库名称不同的历史档案不自动合并。
4. 当前商品汇总按 `product_code`、`product_name`、`color_name`、`color_spec` 分组；流水必须精确匹配同一组，包含空值、空字符串的区别，不用货号模糊搜索代替明细定位。
5. 汇总卡片统计全部匹配记录，不是当前页小计；超出页码或期间无流水时仍需正确保留合计和期初结转。
6. 同一明细页面的卡片、记录数、流水页使用同一次数据库查询结果，避免读到不同时间的数据。
7. 返回商品汇总和关闭库存窗口后刷新上一级数据；加载中或失败时隐藏旧卡片数字，不能将查询失败显示为零库存。
8. 对账时使用同一日期范围和同一数据快照。不同页面分别查询期间发生业务写入，结果仍可能有时间差，不能据此直接认定算法错误。

### 4.3 缓存与详情刷新

库存等实时统计请求使用 `cache: "no-store"`；主动使用业务缓存的看板必须定义缓存键、有效期和强制刷新行为。当前工厂渠道看板有约定的 5 分钟缓存，不要求所有页面一律取消缓存。

商品详情的开发要求：打开时获取最新详情，或在数据更新后明确使列表与详情缓存失效；不能长期只渲染列表旧对象。请求失败应提示，不能悄悄回退为旧对象并当成最新数据。

**待完善：**当前 `ProductDetailDialog` 仍直接接收列表传入的商品对象，尚未在打开时重新查询详情。M06、M17 已有尺寸却曾显示空值属于这类刷新问题；M45 此前核对的源表字段本身为空，不能通过刷新或套用其他颜色修补。本条是后续改造要求，不代表该问题已修复。

## 5. Excel 导入、导出与后台任务

### 5.1 导入前的检查

- 文件读取、模板识别、日期、数值、必填字段和档案匹配均在写入前检查。预检查不写入业务数据。
- 商品型经营历程导入必须校验明细商品能匹配对应品牌商品信息档案；找不到时列出编码，提示“请联系商品部维护商品信息档案后再导入”，本批不写入。
- 按模板预检查、正式导入、明细重新导入等入口保持一致；费用类单据不作商品档案校验。被明确取消的单据按现有跳过规则处理。
- 保留供应商、客户、仓库、科目、尺码等已有检查，不为绕过报错默默创建或错配档案。
- 模板中“经手人”为空、空串或仅空白时，用当前登录账户的 `display_name`；无可用姓名时沿用现有账户回退规则使用 `username`。已有姓名保留。
- 经手人补齐发生在模板校验和分组之前，预检查与正式导入使用相同处理；普通导入、后台批次、旧版“制单人”列均应覆盖。

### 5.2 大文件、事务与重复提交

| 项目 | 当前实现或要求 |
|---|---|
| 经营历程/采购相关上传文件上限 | 单文件 100MiB，页面提示 100MB；统一常量位于 `upload-limits.mjs` |
| Next.js 请求体代理空间 | 101MiB，为 multipart 边界预留空间；反向代理限制需单独核对 |
| 商品资料候选查询 | 每批最多 5,000 个候选，避免数据库参数超限 |
| 通用模板明细写入 | 最多 5,000 行一批；同结构且至少 100 行的 PostgreSQL psycopg 批次可使用 COPY |
| 模板主单据汇总 | 每批最多 1,000 张单据在数据库内汇总 |
| 事务边界 | 明细、主单据及成功任务状态同事务提交或回滚 |
| 请求去重 | 同一任务 ID、文件及参数不重复执行；新 ID 仍需检查业务冲突 |

分批写入不等于分批提交，也不代表文件解析全程只占一批内存。模板解析和候选展开仍可能保存多组数据；大文件优化必须检查整个流程的内存峰值，不能只因使用 `read_only=True` 或 COPY 就宣称不会占满内存。

后台模板导入使用 `queued → running → succeeded/failed` 状态。任务状态保存在数据库，同一浏览器会话可以继续核验；连接中断表示结果待确认，不等于失败。不得在未确认结果时自动重新导入。

失败信息应保留批次编号和可处理的业务原因；完整诊断放在后端日志，用户界面不展示整段 SQL 参数。服务重启不保证未完成任务继续运行，不提供实际不存在的断点续传承诺。

### 5.3 导出

- 导出范围明确区分当前筛选、勾选记录、当前品牌和全量，按钮及说明不得混淆。
- 列表、数量合计、分页、跨页选择与导出共用已提交条件；跨页全选使用服务端 ID 快照，不通过翻页循环抓取。
- 使用品牌配置中的名称生成文件名、工作表名和品牌列；新品牌不需要硬编码名称。
- 工作表名称处理非法字符和 31 字符限制；货号、条码、日期、金额格式保持可用。
- 导出不含回收站商品、排除清单商品或未授权成本。缺失字段保留缺失，不从其他品牌补造。

## 6. 查询性能、数据库与运维规则

1. 筛选、聚合、计数和分页优先在数据库完成，不把全部明细加载进 Python 或浏览器再计算。
2. 列表接口只返回页面所需数据；避免逐行商品查询、逐仓库重复全表扫描等 N+1 模式。
3. 统计优化同时验证正确性、查询数、代表性数据量和内存；不能只测空表耗时。
4. 可以复用聚合结果的计数、合计和分页尽量共享查询。不得为提速放松完成状态、品牌或删除条件。
5. 诊断先限定货号、仓库、时间和返回数量；只读排查采用只读事务、语句超时与合理资源上限，避免在业务库无界扫描或运行大并行任务。
6. 数据库访问用参数化表达式；动态表名来源于已验证配置，不拼接未经验证的用户输入。
7. 结构变更提供迁移、适用版本及回退说明；旧版 `schema.sql` 是结构快照，不能直接覆盖已有业务库或代替升级迁移。
8. 维护脚本优先提供只读预览、目标范围、幂等策略、处理数量和结果日志；修复生产数据前核对依据与影响范围。
9. 定时任务说明实际计划、业务日期、时区、来源文件、目标表和保留规则。执行时间以当前调度配置为准，不把历史聊天时间直接当作在线配置。
10. 修改定时任务时检查重复触发、互斥锁、失败重试、同日幂等及历史清理范围；不因改执行时间顺带重复导入。

## 7. UI 视觉基础

### 7.1 风格与主题

项目采用**中性灰阶、深色侧栏、浅色内容面板、紧凑业务表格**。强调层级清楚、信息可读、操作稳定；不为单个页面另造一套字体、品牌色和装饰体系。

颜色统一取自 `frontend/app/globals.css` 的语义变量；用 Tailwind 语义类引用。普通面板避免直接写死白色或黑色，以兼容深浅主题。

| 用途 | 使用方式 | 当前浅色 / 深色变量值 |
|---|---|---|
| 页面背景 | `bg-background` | `oklch(0.982 0 0)` / `oklch(0.13 0 0)` |
| 主要文字 | `text-foreground` | `oklch(0.145 0 0)` / `oklch(0.96 0 0)` |
| 面板、表单 | `bg-card` | `oklch(1 0 0)` / `oklch(0.18 0 0)` |
| 主按钮 | `bg-primary text-primary-foreground` | 深灰 / 浅灰反转 |
| 次级背景 | `bg-muted` | `oklch(0.955 0 0)` / `oklch(0.24 0 0)` |
| 辅助文字 | `text-muted-foreground` | `oklch(0.48 0 0)` / `oklch(0.7 0 0)` |
| 边框 | `border-border` | 灰色 / 白色 10% 透明度 |
| 危险操作、错误 | `text-destructive` 等 | 使用主题的危险色 |
| 焦点 | `focus-visible:ring-ring` | 保持统一的可见焦点 |

入库、成功可使用绿色；出库、错误可使用红色；处理中、待确认可使用琥珀色。必须同时提供“入库”“出库”“失败”等文字，不能仅靠颜色表达。深色主题需单独检查业务色的对比度。

### 7.2 页面、间距和字号

优先复用以下全局类：

| 类名 | 用途 | 当前实现 |
|---|---|---|
| `app-page` | 页面外层 | 小屏水平 12px、垂直 16px；`sm` 起水平 20px、垂直 24px |
| `app-content` | 常规内容 | 居中、`max-w-6xl`、区域间距 20px |
| `app-content-wide` | 宽表格页面 | 居中、最大 1600px、区域间距 20px |
| `app-content-narrow` | 简单表单或设置 | 居中、`max-w-4xl` |
| `page-header` | 页面标题和操作 | 可换行、圆角、边框、面板背景、轻阴影 |
| `page-title` | 页面标题 | `text-2xl font-semibold` |
| `page-subtitle` | 说明文字 | `text-sm text-muted-foreground` |
| `surface-panel` | 筛选、品牌、统计等区域 | `rounded-2xl`、统一边框与轻阴影 |
| `table-panel` | 表格外壳 | `rounded-2xl`、边框、裁切与轻阴影 |
| `table-head-row` | 表头 | 次级背景、细边框、12px 辅助文字 |
| `table-row` | 数据行 | 轻量悬停高亮 |

新布局建议以 4px 为间距基准：行内 4–8px，表单与工具栏 8–12px，面板内边距 12–20px，大区域 16–24px。沿用相邻页面，不为对齐某个截图堆叠无依据的固定偏移。

正文和表格常用 14px；标签、表头和辅助说明常用 12px；统计数字常用 18–24px。业务数值使用 `tabular-nums`；货号、单号、条码可用 `font-mono`，长中文说明保持正常字体。

字体使用布局中加载的本地 Geist、Geist Mono 及系统中文回退；不依赖外部字体请求。全局基础圆角 `--radius` 为 `0.55rem`；字段、按钮和大面板按现有组件层级取值。

## 8. UI 组件与交互规则

### 8.1 页面信息结构

列表页面建议保持以下顺序：

`页面标题/说明/主要动作 → 查询区域 → 汇总与结果说明 → 表格或卡片 → 分页`

筛选较多时支持换行或合理折叠；主按钮与查询按钮不能因横向滚动被完全隐藏。库存、金额等汇总放在结果附近，标明期间与范围，避免用户误认为是当前页小计。

### 8.2 按钮

必须使用项目 `Button`，选择现有变体：

| 变体 | 使用场景 |
|---|---|
| `default` | 查询、保存、确认等当前区域主要操作 |
| `outline` | 清空、取消、返回、导出等常规次要操作 |
| `secondary` | 需要有背景的次级动作 |
| `ghost` | 表格行内查看、编辑等操作 |
| `destructive` | 删除等危险操作 |
| `link` | 文字链接式操作 |

当前按钮尺寸：`xs` 24px、`sm` 28px、默认 32px、`lg` 36px；图标按钮分别对应 24/28/32/36px。输入框默认高 36px。不要按其他 shadcn 模板假定默认按钮高 40px。

- 同一工具栏对齐高度；密集表格允许紧凑按钮，触屏操作建议扩大到至少 44px 的可点击区域。
- 普通按钮用“查询、清空、新增、导入、导出、保存、取消、返回”，同类操作跨页面保持命名一致。
- 只含图标时必须有 `aria-label`，建议同时有 `title`；装饰图标设为对辅助技术隐藏。
- 提交中防止重复点击并显示“保存中…”等状态；耗时后台任务显示任务状态，不让按钮无限转圈而无说明。
- 删除确认必须说明对象与数量；批量删除明确是当前页还是跨页选择范围。

### 8.3 表单与选择器

- 字段有可见标签，`Label` 与输入框关联；必填标识和错误说明靠近字段。
- placeholder 用作示例或输入提示，不代替字段名称；只读、禁用、无权限分别表达。
- 错误后保留已输入内容；保存成功后刷新相关列表和统计，关闭流程清楚。
- 商品年份、季节、品名选项从已有商品取得，支持输入模糊匹配、多值选择；候选项来源与最终检索范围保持一致。
- 同字段多选通常为“匹配任意选中项”，不同字段之间为“同时满足”；若模块不同，明确说明。
- 搜索型下拉复用 `ProductOptionSelect`、`ProductMultiOptionSelect` 等现有能力，不用超长原生列表替代。
- 下拉限制高度、内部滚动、避让屏幕边缘；弹窗中的下拉使用能正确处理 Portal 和层级的组件，不能被 `overflow-hidden` 裁切。
- 方向键选择、回车确认、Esc 收起、Tab 离开必须可用；中文输入法组词时不触发查询。
- 多行货号、经手人搜索应说明分隔方式；回车搜索、Shift+Enter 换行的区域遵循现有实现，不把换行错误当作提交。
- 日期范围复用 `DateRangeControl`，单日期复用 `DatePicker`。查询日期和预计交付日期的限制不同，不给所有日期控件强加“不得选未来”。

### 8.4 表格、分页与排序

- 文本左对齐，数量和金额右对齐，行内操作居中或右对齐；数值列保持统一精度与对齐。
- 使用语义化 `table/thead/tbody/th/td`；表头内容清楚，排序列提供 `aria-sort`。
- 宽表格在容器内部横向滚动，不挤压到内容重叠；必要时固定表头和关键标识列。
- 固定表头需有不透明背景；冻结列与表头交叉处层级正确，不能让滚动内容穿透。
- 长摘要、路径、品名允许截断，但提供完整查看方式；关键货号和单号优先保持可识别。
- 分页展示总条数、当前范围、每页数量；重新查询或修改筛选后回到第一页。
- 每页条数沿用各业务模块已有配置，不把某个页面的选项强行用于全部页面。
- 跨页勾选与页面展示分开管理；重新提交筛选或切换业务范围后清除不适用选择。
- 精细表等动态筛选必须真正传给后端，并联动合计、分页和导出；不能只改变下拉状态或当前页可见行。

### 8.5 弹窗、详情与层级

- 复用 `Dialog`、`ConfirmDialog`、`MessageDialog`，不随意叠加新的全局弹窗机制。
- 小表单建议 `max-w-md` 或 `max-w-2xl`；商品详情和复杂编辑可用 `max-w-5xl/6xl`；库存宽表格按视口限制宽度。
- 高度一般限制在视口的 88%–92%；标题和必要操作保持可见，正文 `min-h-0 overflow-y-auto`，避免整页与弹窗多重滚动失控。
- 当前通用弹窗层为 `z-[120]`，商品下拉 Portal 为 `z-[150]`。新浮层需检查包含关系，不能随意无限提高 z-index。
- 打开后焦点进入弹窗，Tab 在弹窗内循环；关闭后恢复到触发位置；Esc 和点击遮罩遵循组件约定。
- 有未保存内容或写入正在进行时，要明确退出行为；关闭后台任务窗口不代表取消导入，页面仍需可核验任务。
- 详情的货号、品牌、图片、分组字段保持清晰；不得把隐藏字段误当作没有数据。

### 8.6 加载、空数据、错误与成功

| 状态 | 必须呈现的内容 |
|---|---|
| 初次加载 | 加载指示，避免闪现“暂无数据” |
| 改条件重新查询 | 明确加载状态；旧汇总数字隐藏或明确标为旧结果 |
| 成功但无数据 | “该期间暂无库存流水”等具体空态，允许调整条件 |
| 请求失败 | 业务错误和可执行的重试方式，不显示伪造的零值结果 |
| 后台处理 | 批次、状态、继续核验入口；不重复创建任务 |
| 操作成功 | 显示必要结果并刷新受影响列表、详情、合计 |

成功、失败和加载提示使用中文。文案直接说明发生了什么、影响范围和下一步；避免把数据库表名、SQL、技术堆栈放入业务操作说明。

### 8.7 响应式与可访问性

- 保持桌面业务效率，同时验证 375px、768px、1280px 和常用桌面宽度；不要只按单张截图尺寸设计。
- 页面容器使用 `min-w-0`、换行和内部滚动；小屏上按钮、关闭入口和分页仍可达。
- 所有可交互元素有可见焦点；不用不可聚焦的 `div` 代替按钮。
- 普通文字建议满足 WCAG AA 的 4.5:1 对比度，大字和必要非文本元素按适用标准检查。
- 状态不仅依赖颜色；错误适当使用 `role="alert"`，后台状态可用 `role="status"` 或温和的 `aria-live`。
- 动效简短，遵守 `prefers-reduced-motion`；不加入影响表格阅读的持续装饰动画。
- 图片有合理替代文本、加载失败占位和尺寸约束，避免图片出现后挤动整张表格。

## 9. 验证、评审与交付

### 9.1 最小验证范围

| 修改类型 | 需要验证 |
|---|---|
| 筛选、分页、导出 | 已提交条件一致，多选、清空、换页、跨页选择、导出范围 |
| 商品字段或档案匹配 | 对应品牌、相似货号、原始货号、颜色尺码、空值、回收站排除 |
| 导入 | 预检查、普通导入、后台批次、覆盖/新增/跳过、失败回滚、重复提交 |
| 统计 | 边界日期、期初结转、调拨两端、未完成与已删除、空页、全量合计、并发更新 |
| 详情或缓存 | 数据更新后重新打开、旧响应迟到、返回上级、请求失败不显示旧结果 |
| 权限 | 有权、无权、未登录、成本及导出等独立权限 |
| 布局和组件 | 深浅主题、窄屏、键盘、下拉遮挡、滚动、长文本和加载状态 |

用例优先验证用户可观察的行为和业务不变量，不只断言函数内部调用顺序。纯文档修改检查链接、路径、术语和代码示例即可；不为低风险文字调整运行全量业务测试。

测试数据使用隔离 SQLite 或专用测试数据库；运行数据库集成测试前明确 `TEST_DATABASE_URL` 指向专用实例。现有重建表夹具可能执行 `drop_all`，禁止指向业务库。

### 9.2 常用检查命令

以下在仓库根目录执行。当前 Windows 环境使用 `pnpm.cmd` 和 `backend/.venv/Scripts/python.exe`；其他环境按实际可执行文件调整。

```powershell
# 前端类型检查
pnpm.cmd --dir frontend run typecheck

# 只运行受影响的组件测试，路径按改动替换
pnpm.cmd --dir frontend exec vitest run components/inventory-admin/warehouse-inventory-dialog.test.tsx

# 定向检查前端文件，不对整个仓库自动修复
pnpm.cmd --dir frontend exec eslint components/inventory-admin/warehouse-inventory-dialog.tsx

# 新增后端验证放入忽略目录；指定本次独立临时目录
backend/.venv/Scripts/python.exe -m pytest -c backend/pyproject.toml outputs/logs/test_inventory_template_handler_defaults.py -q -p no:cacheprovider --basetemp=outputs/logs/pytest-handler-check

# 检查空白错误及提交范围
git diff --check
git status --short
git diff --name-only
```

`--basetemp` 指定的目录可能被 pytest 清理，必须使用该次测试专用目录，不能指向业务文件或手工资料目录。不要通过 `pnpm test -- ...` 猜测参数传递结果，定向 Vitest 使用上面的 `exec vitest run` 形式。

存在原有失败用例时，说明失败原因及与当前改动的关系；不要为得到全绿结果放松业务校验、隐藏失败或修改用户要求不上交的测试目录。

### 9.3 评审和发布要求

- 交付说明包含：解决的问题、最终行为、验证结果、已知限制、是否涉及迁移及如何生效。
- 文档不能把抽样核对描述成全库证明，也不能把本地源码验证描述成线上已部署。
- 提交前检查文件清单；排除 `.env`、日志、导出 Excel、临时数据库、缓存、`outputs/` 和 `backend/tests/`。
- 后端修改通常需手动重启后端；前端生产模式需重新构建并启动，源码保存不等于生产页面已更新。
- 仅在需要构建验证或发布时执行构建；不要为文档工作重启服务。构建可能影响正在使用的目录，按现有 `NEXT_DIST_DIR` 方案评估。
- 有数据库迁移时写清执行顺序和回退条件；没有结构变更时明确不需要迁移。
