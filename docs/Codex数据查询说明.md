# Codex 数据查询说明

## 1. 目的与边界

本说明用于支持用户直接以自然语言查询经营数据。Codex 负责理解需求、调用受控只读查询工具或业务接口、按统一口径汇总并说明数据日期和限制；不得让模型直接猜测表名、字段含义或自行执行任意 SQL。

适用范围：商品档案、商品货品表、精细表、库存、销量、订单、工厂渠道看板、定时任务与操作审计。

当前支持品牌：

| 品牌名称 | 业务标识 |
| --- | --- |
| 千百度男鞋 | `cbanner_mens` |
| 千百度女鞋 | `cbanner_womens` |
| 烟斗 | `yandou` |
| 伊伴 | `eblan` |

## 2. 查询原则

1. 默认返回“数据截至日期、统计口径、结果、异常或缺失说明”。
2. 先解析品牌、货号/款号、时间范围、平台、尺码、指标和排序；用户未说明时，采用本说明的默认值。
3. 跨年销量、订单、历史快照必须使用 `v_` 统一视图或封装业务接口，不直接只查 `*_2024`、`*_2025`、`*_2026` 的逻辑父表。
4. 数量较大时默认返回前 20 条及总数；用户要求全量时，应导出受控文件或按页返回，不在对话中堆放大量明细。
5. 同一指标存在多个来源时，严格按本说明的优先级；禁止将重叠来源重复相加。
6. 无数据时先检查数据覆盖日期、品牌、货号映射和任务状态，再明确回答“当前没有数据”或“数据截至某日”。
7. 除已授权的人工运营字段外，查询工具只读。修改商品字段、重跑任务、导出数据需走明确的受控操作并记录审计日志。

## 3. 术语与默认口径

### 3.1 编码与匹配

| 术语 | 定义与使用规则 |
| --- | --- |
| 货号 | 商品维度主编码。货品表当前千百度男女鞋以管家婆 `goods_code` 为准。 |
| 款号 / 原始货号 | 去除货号末尾两位颜色编码后的聚合维度；原始值优先取 `original_goods_code` / `original_sku`。 |
| 尺码 | 通过唯品尺码字段、聚水潭 `color_spec` 或历史销量 `size` 解析。正常鞋码为 34-44；洞洞鞋尺码为 `225-230` 至 `250-255`。 |
| 货号映射 | 先精确匹配货号，再按“源商品编码以货号开头”匹配；仅在款号唯一对应一个货号时可按款号回退。多个货号共享同一款号时，不得擅自分摊销量。 |
| 品牌 | 必须使用业务标识过滤，不能仅以货号前缀推断。 |

### 3.2 时间

| 用户表述 | 默认解释 |
| --- | --- |
| 今天 / 昨天 | 以对应日销表中的最大 `sales_date` 为业务最新日。回答中必须写出实际日期；“昨天销量”是该最新业务日销量，并不保证等于系统自然日昨天。 |
| 近 7 天 | 含最新业务日的连续 7 天。 |
| 上周 | 最新业务日往前第 8 至第 14 天的连续 7 天。 |
| 本月 / 月销量 | 从最新业务日所在月 1 日至最新业务日。 |
| 年度销量 / 年销量 | 指定自然年 1 月 1 日至该年数据最新日；未指定时为当前年。 |
| 历史日期 | 经营表按用户指定 `snapshot_date` 的已固化快照返回，不能用当前数据倒推。 |

### 3.3 传统、直播、清仓

渠道先由历史店铺映射表匹配，再按渠道原文关键词兜底：

| 分类 | 判定规则 |
| --- | --- |
| 清仓 | 原渠道包含“清仓”，或归类为 `达播清仓`、`拼多多清仓`。 |
| 直播赛道 | 非清仓且归类为 `直播赛道`。 |
| 传统赛道 | 直播赛道和清仓之外的全部销量。 |

货品表的平台明细使用：`唯品`、`天猫`、`得物`、`拼多多`、`京东`、`商品卡`、`直播赛道`、`达播清仓`、`拼多多清仓`、`其他`。

关键词兜底规则：包含“唯品”“天猫”“得物”“京东”“商品卡”归入相应平台；“拼多多 + 清仓”归 `拼多多清仓`，否则归 `拼多多`；“达播 + 清仓”归 `达播清仓`；含“直播”归 `直播赛道`；不能识别归 `其他`。

## 4. 业务对象与受控数据入口

### 4.1 商品基础信息

| 需求 | 首选入口 | 规则 |
| --- | --- | --- |
| 千百度男女鞋当前基础信息 | 商品档案查询接口或 `gj_merged_product_info` 联合品牌商品档案 | 以最新 `source_date_value`、对应 `fine_table_brand` 的管家婆记录为主；商品档案补充图片、年份、季节、颜色、成本等管家婆未提供字段。 |
| 烟斗、伊伴当前基础信息 | 对应品牌商品档案表 | 使用 `yandou_products`、`eblan_products`，并按接口既定的成本补充规则处理。 |
| 材质、工厂货号、供应商、上市日期 | `gj_merged_product_info` | 千百度男女鞋优先取管家婆的 `factory_code`、`primary_supplier`、材质、`launch_date`。 |
| 成本 | 商品档案查询接口 | 成本优先采用聚水潭价格资料的有效成本；无有效值才保留商品档案成本。 |
| 手工运营字段 | `product_goods_overrides` | `所属平台`、`四级分类`、`商品角色`、`类型`、`抖音爆款`、`清仓`、`备注` 及补单字段。它不是商品主档。 |

**重要：** 千百度男鞋、女鞋的“当前货品表”和“当前精细表”必须使用相同的管家婆主商品集合。查询基础信息时，不能直接以 `cbanner_mens_products` 或 `cbanner_womens_products` 的全量行数作为当前商品数。

### 4.2 货品表

优先调用货品表查询接口，而不是自行拼接所有来源：

| 查询类型 | 受控入口 / 数据源 | 说明 |
| --- | --- | --- |
| 当前货号明细 | `GET /product-goods` | 汇总基础资料、手工字段、库存、日销、历史销量与订单。 |
| 当前款号汇总 | `GET /product-goods?view=style_summary` | 以去末两位颜色码的款号聚合；销量、库存、尺码明细均求和，不展示单一颜色。 |
| 缺货风险 | `GET /product-goods?view=shortage_risk` | 使用全量库存、可用库存、库存销售天数和尺码风险规则。 |
| 指定历史日期 | `GET /product-goods?snapshot_date=YYYY-MM-DD` | 读取 `v_product_goods_detail_snapshots` 和库存快照；只返回已保存的快照日期。 |
| 可筛选字段值 | `GET /product-goods/filter-options` | 用于年份、季节、工厂、款号、货号等条件的候选值。 |

货品表重点字段口径：

| 字段 / 指标 | 口径 |
| --- | --- |
| 在仓库存 + 进货仓 | `jst_full_stock.actual_stock_qty + purchase_warehouse_stock_qty`，按货号与尺码汇总。 |
| 在途库存 | `purchase_in_transit_qty + transfer_in_transit_qty + return_in_transit_qty`；当前全量库存按尺码可拆分。 |
| 库存合计 | 在仓库存 + 进货仓 + 在途库存。 |
| 缺货库存 | 全量库存的 `available_qty < 0` 的缺口，按尺码汇总。 |
| 昨日销量 / 前日销量 / 昨比前日 | 以两张日销表中最大可用业务日为“昨日”；昨比前日 = 最新业务日销量 - 前一业务日销量。 |
| 正价货架销量 | 当日或近 7 天内所有非清仓渠道销量，包含传统和直播赛道。 |
| 清仓销量 | 当日或近 7 天内清仓渠道销量。 |
| 近 7 天周销量 | 当前最新业务日及前 6 日的销量。 |
| 总销量 | 当前日销、唯品日销和历史销量按统一货号去重汇总后的销量。唯品数据优先用唯品日销；同一货号、同一天已有唯品日销时，聚水潭中归为唯品的记录不重复累计。 |
| 总订单量 | 历史订单表按原始货号统计；当前日销的订单量为补充，不得与同一来源重复相加。 |
| 年度 / 月度销量 | 优先取 `product_goods_sales_periods` 的预计算值；历史年度覆盖受已导入数据限制。 |
| 销售明细（尺码） | 当前近 14 天销售按尺码汇总。 |
| 补单明细、补单后库存/尺码/合计/周转天数 | 当前为人工维护字段，未填写时返回空值，不得自行推断为 0。 |
| 断码 SKU | 当前暂不提供可靠来源，返回空值；不得用库存为 0 自动替代。 |

### 4.3 销量与订单

| 数据内容 | 首选入口 | 关键字段 | 规则 |
| --- | --- | --- |
| 唯品逐日销量 | `v_vip_daily_sales` | `sales_date`、`goods_code`、`style_code`、尺码、`sales_quantity` | 唯品销量的唯一优先来源。 |
| 其他渠道逐日销量 | `v_jst_daily_sales` | `sales_date`、`product_code`、`style_code`、`channel`、`net_sales_quantity` | 平台由 `channel` 和店铺映射归类。 |
| 2024/2025 历史销量 | `v_product_goods_historical_sales` | `brand`、`sales_date`、`product_code`、`original_sku`、`channel`、`size`、`sales_quantity` | 历史工作簿完整覆盖的年份，优先用该来源，避免与补录日销重复。 |
| 历史订单量 | `v_product_goods_historical_orders` | `brand`、`order_date`、`original_sku`、`channel`、`order_quantity` | 用于总订单量和历史订单分析。 |
| 店铺到渠道映射 | `product_goods_shop_channel_mappings` | `brand`、`shop_name`、`channel` | 映射优先于渠道关键词；同一店铺出现多个渠道时属于数据异常，不能任选一个。 |

### 4.4 库存

| 需求 | 首选入口 | 说明 |
| --- | --- | --- |
| 当前库存、在途、库存销售天数 | `jst_full_stock` | 当前全量库存来源，按货号、尺码解析。 |
| 当前尺码在仓库存 | `jst_size_stock` | 当前尺码库存汇总。 |
| 当前采购在途汇总 | `jst_stock_summary` | 用于采购在途的汇总补充。 |
| 指定日期的尺码库存 | `jst_size_stock_snapshots` | 以 `snapshot_date` 查询。 |
| 历史货品表完整经营状态 | `v_product_goods_detail_snapshots` | 优先于用当前库存表倒推。 |

### 4.5 精细表

| 需求 | 首选入口 | 说明 |
| --- | --- | --- |
| 当前精细表 | `GET /fine-table` | 由接口统一组合唯品罗盘、商品运营、订单和库存指标。 |
| 当前筛选候选值 | `GET /fine-table/filter-options` | 与精细表当前商品集合一致。 |
| 精细表历史日期 | `v_fine_table_snapshot_rows` + `fine_table_snapshot_batches` | 必须按品牌和快照日期定位。 |
| 唯品 UV、CTR、收藏、拒退件数、拒退率 | `vip_product_daily` 或规范化唯品周期视图 | 需同时说明 `report_type`、`period` 和数据日期。 |

### 4.6 工厂渠道看板

优先调用 `GET /product-goods/factory-channel-dashboard`。看板按工厂、销售年份、时间范围、传统/直播/清仓汇总销售数据；对 2024、2025 等已由历史工作簿完整覆盖的年度优先使用历史销量，不能再叠加部分日销补录。

### 4.7 定时任务与审计

| 需求 | 受控入口 | 规则 |
| --- | --- | --- |
| 今日 / 某日实际执行记录 | `scheduled_task_runs` | 返回 `task_name`、`status`、`started_at`、`finished_at`、`duration_ms`、`exit_code`、`error_summary` 和 `log_path`。每次重跑保留一行。状态失败时可建议重跑，但不得自行重跑。 |
| 业务日期导入状态 | `scheduled_task_statuses` | 按 `task_name + business_date` 查看某个数据日期的导入状态、尝试次数和来源文件；同日重跑会更新状态而不是新增运行历史。 |
| 操作日志 | `operation_logs` 对应接口 | 必须走现有权限过滤。超级管理员的操作不向普通账户展示。 |

## 5. 查询执行流程

1. **识别意图**：确定是商品、销量、库存、订单、精细表、货品表、工厂看板、任务还是审计。
2. **补齐参数**：识别品牌、货号/款号、尺码、平台、日期、排序和粒度。缺少品牌且货号无法唯一识别时，先询问品牌；缺少日期时使用最新业务日并明确说明。
3. **确定粒度**：货号、款号、工厂、店铺、平台、尺码、日/月/年只能选择用户要求的粒度。款号汇总不得混入颜色行。
4. **选择入口**：优先调用本说明中的业务接口或 `v_` 视图；只有接口无法提供的字段才使用受控只读 SQL 模板。
5. **执行校验**：检查品牌过滤、来源最大日期、货号/款号匹配方式、是否存在唯品与聚水潭重叠、是否存在空值。
6. **组织答复**：先给结论，再给简表；注明“数据截至”、来源、计算口径。空值写“暂无数据”，不能写成 0，除非源记录明确为 0。
7. **审计**：记录查询人的身份、问题摘要、参数、数据日期、调用的受控工具和返回行数；不记录用户不需要的明细数据到日志。

## 6. 权限与数据安全

1. 商品货品表、工厂渠道看板仅向超级管理员及商品部、开发部、运营部开放。
2. 成本、供应商联系方式、采购单价、订单明细属于敏感经营信息，应按现有后端权限策略返回；权限不明确时不展示明细，先请求授权或仅给脱敏汇总。
3. 操作日志中，超级管理员操作只允许超级管理员及系统管理员按既有过滤规则查看。
4. Codex 的数据库能力必须是只读白名单：允许业务接口、`v_` 视图和明确列出的查询模板；禁止 `INSERT`、`UPDATE`、`DELETE`、`DDL`、任意文件路径访问及未限制的全表扫描。
5. 所有 SQL 必须参数化，并强制品牌、日期范围、行数上限。默认明细上限 200 行，聚合结果上限 100 行。
6. `raw_payload` 仅用于导入问题追溯，不能作为常规检索条件，也不应直接返回给用户。

## 7. 标准问法与返回方式

| 用户问题示例 | Codex 执行方式 | 返回重点 |
| --- | --- | --- |
| “查千百度男鞋 QC153883D54 昨日销量和库存” | 货品表当前货号查询 | 货号、最新业务日、昨日销量、在仓、在途、库存合计、尺码明细。 |
| “千百度女鞋近 7 天得物销量前十” | 日销视图按平台归类后汇总 | 统计区间、货号/款号、得物销量、总销量；说明是否含退货后的净销量。 |
| “某款号各颜色库存和销量” | 货号明细，按原始货号筛选 | 每颜色货号、尺码库存、近 7 天销量、合计。 |
| “某工厂今年传统、直播、清仓各卖多少” | 工厂渠道看板 | 实际日期范围、三类销量及占比，明确传统=非直播且非清仓。 |
| “伊伴 2026 年上市款有哪些卖点” | 商品档案查询 | 货号、上市日期、卖点；无卖点写暂无数据。 |
| “精细表某货号唯品拒退率是多少” | 精细表 / 唯品周期指标查询 | 指标周期、快照或报告日期、拒退件数、拒退率；不混用不同周期。 |
| “今天定时任务有没有失败” | 任务状态查询 | 每个失败任务的名称、业务日期、开始/结束时间、错误摘要、重试次数。 |

```text

统计口径：近 7 天，含 2026-07-28 至 2026-08-03；销量为唯品日销与聚水潭净销量按规则去重汇总。

| 货号 | 款号 | 唯品 | 天猫 | 得物 | 直播 | 清仓 | 合计 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| ... | ... | ... | ... | ... | ... | ... | ... |

说明：未匹配到渠道的数据归入“其他”；空值表示当前无可用来源，不等同于 0。
```

## 8. 异常处理规则

| 情况 | 处理方式 |
| --- | --- |
| 用户未说明品牌，但货号在多个品牌存在 | 询问品牌，不进行跨品牌默认汇总。 |
| 用户提“昨天”，但日销最新日期并非自然日昨天 | 返回最新业务日并解释源数据未更新到自然日昨天。 |
| 唯品与聚水潭同日同货号同时存在 | 唯品日销优先，排除聚水潭中已识别为唯品的重复记录。 |
| 店铺渠道映射冲突 | 标记为“待维护映射”，不擅自归类到传统、直播或清仓。 |
| 历史日期不存在快照 | 明确没有该日期的已保存历史视图，并列出最近可用快照日期。 |
| 指标字段为空 | 区分“源表未导入”“当前字段为人工维护”“源表明确为 0”；不以默认值掩盖。 |
| 查询过大或计算耗时 | 先返回汇总/Top N，提示可导出；禁止无日期条件的超大明细查询。 |

## 9. 工具设计建议

正式接入时，建议给 Codex 暴露以下受控工具，而不是开放 PostgreSQL 账户：

| 工具 | 必填参数 | 输出 |
| --- | --- | --- |
| `query_product_goods` | `brand`，可选货号/款号/日期/平台/尺码/视图 | 当前或历史货品表统一结果。 |
| `query_fine_table` | `brand`，可选货号/日期/筛选条件 | 精细表经营指标。 |
| `query_sales_summary` | `brand`、日期范围、粒度、可选平台/货号/工厂 | 统一销量与渠道汇总。 |
| `query_inventory_summary` | `brand`、货号或款号、可选快照日期 | 在仓、在途、缺货、尺码库存。 |
| `query_factory_channel_dashboard` | `brand`、销售年份、可选工厂/日期范围 | 工厂传统/直播/清仓汇总。 |
| `query_task_status` | 可选日期、任务名称 | 定时任务状态和失败原因。 |
| `export_query_result` | 已授权查询任务 ID、格式 | 带字段定义和数据截至日期的导出文件。 |

每个工具都应返回：`data_as_of`、`source_tables`、`metric_definition`、`warnings`、`row_count`。这样 Codex 才能向用户解释结果，而不是只给一串数字。

## 10. 维护要求

以下任一变更必须同步更新本说明及数据库表目录：新增/删除品牌、表或视图；字段改名；销量或库存口径变化；渠道映射调整；定时任务时间或来源变动；权限变化；历史数据补录范围变化。
