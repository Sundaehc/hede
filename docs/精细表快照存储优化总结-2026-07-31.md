# 精细表快照存储优化总结

日期：2026-07-31

## 背景

精细表需要按任意历史日期查看完整商品状态。原实现每天按品牌把约 6 万条商品行的完整 JSON 写入年度快照表，2024 至 2026 年快照表合计约 91 GB，是数据库的主要空间来源。

原有历史查询、筛选、分页和导出依赖完整商品行，因此本次不删除每日历史，也不改变前端接口。

## 已完成优化

### 1. 去重存储结构

新增两张全局内容表：

- `fine_table_snapshot_payloads`：稳定商品属性，例如货号、年份、季节、工厂、材质、图片和商品档案字段。
- `fine_table_snapshot_metrics`：每日经营指标，例如价格、销量、库存、在途、风险、拒退和近几日销售明细。

新增按年引用表：

- `fine_table_snapshot_refs_2024`
- `fine_table_snapshot_refs_2025`
- `fine_table_snapshot_refs_2026`

引用行只保留批次、日期、货号、原始货号、排序位置、稳定属性 ID 和每日指标 ID。稳定属性及每日指标按内容哈希去重；同一商品基础信息跨日期不再重复存储。

### 2. 新旧快照兼容

- 新生成的每日快照写入引用表。
- 历史日期查询优先读取引用表并合并为原来的完整商品行。
- 未迁移日期自动回退读取 `fine_table_snapshot_rows_YYYY` 旧表。
- 前端接口、日期选择、搜索、货号前缀筛选、分页和导出返回结构不变。

### 3. 关联任务兼容

- 每日精细表 Excel 导出已支持读取新引用表。
- 历史 Excel 快照导入已切换为去重写入。
- 排除货号任务会同时清理旧行表和新引用表，并重算快照总行数。
- Smile 精细表导入清理逻辑同时兼容旧行表和新引用表。
- 快照批次元数据、稳定属性、每日指标和引用行在同一事务内写入，快照更新失败不会留下行数不一致的半成品批次。
- 新增孤立内容清理工具；仅清理没有被任何年份引用表使用的稳定属性和每日指标，不触碰有效历史快照。

### 4. 数据库结构

已在当前数据库创建：

- `fine_table_snapshot_payloads`
- `fine_table_snapshot_metrics`
- `fine_table_snapshot_refs_2024`
- `fine_table_snapshot_refs_2025`
- `fine_table_snapshot_refs_2026`

新增 Alembic 迁移文件：

`backend/alembic/versions/20260731_0049_fine_table_snapshot_dedup.py`

当前数据库的 Alembic 记录停在 `20260611_0023`。为避免一次执行后续全部历史迁移，本次没有运行 `alembic upgrade head`；新增表已通过新 schema 单独创建。后续应先核对既有迁移的实际执行状态，再统一校正 Alembic 版本记录。

## 历史数据迁移

新增脚本：

`backend/scripts/migrate_fine_table_snapshot_dedup.py`

推荐按日期分批执行：

```powershell
cd E:\hede\backend
uv run python -m scripts.migrate_fine_table_snapshot_dedup --snapshot-date 2026-07-30
```

默认只创建新引用数据，不删除旧 JSON 行。通过页面历史日期、导出结果和行数核对后，再对同一天执行：

```powershell
uv run python -m scripts.migrate_fine_table_snapshot_dedup --snapshot-date 2026-07-30 --delete-legacy
```

`--delete-legacy` 只会删除该日期已成功迁移批次的旧行，不删除批次、去重内容或其他日期数据。建议先迁移最近 7 天，再按月或按年逐步执行，避免一次读取和重写 90 GB 历史数据。

已完成 2026-07-30 的首日迁移验证准备：4 个品牌、60,930 行已写入新引用结构，旧 JSON 行仍完整保留。各品牌新旧行数一致：千百度男鞋 19,113、千百度女鞋 14,605、伊伴 9,959、烟斗 17,253。

## 内容维护

更新某个日期快照或排除货号后，旧引用可能不再使用少量稳定属性或每日指标。新增维护脚本默认只输出候选数量：

```powershell
cd E:\hede\backend
uv run python -m scripts.cleanup_fine_table_snapshot_orphans
```

核对输出后，再显式删除孤立内容：

```powershell
uv run python -m scripts.cleanup_fine_table_snapshot_orphans --execute
```

建议在每日快照完成后的低峰期每周执行一次。脚本会汇总扫描现有的 `fine_table_snapshot_refs_YYYY`，没有任何引用表时不会删除数据；有效历史快照的内容不会被清理。

## 预期收益

当前快照表约 91 GB。基础商品属性在相邻日期通常变化较少，拆分后只保存一次；每日变化的销量、库存和价格仍按日期完整保留。

预计完成历史迁移并清理旧行后：

- 快照存储可由约 91 GB 降至约 30 至 45 GB。
- 数据库总占用可由约 124 GB 降至约 63 至 78 GB。
- 实际收益取决于基础属性跨日变化率，应以最近 30 天迁移结果作为最终容量依据。

首日迁移的新结构当前占用约 186 MB：稳定属性 111 MB（60,930 条）、每日指标 57 MB（38,835 条）、2026 引用表 18 MB。旧表尚未删除，因此这不是最终压缩比例。

## 验证与回滚

已完成：

- 精细表结构、筛选和唯品指标测试已覆盖基础读写和筛选回归。
- 新增数据库端到端用例已覆盖“稳定属性复用、每日指标保留、完整行读取”和“孤立内容预览/清理”；当前环境未配置 `TEST_DATABASE_URL` 时，这两项会跳过。
- 后端 Python 编译和 Git 空白检查通过。

验证顺序：

1. 重启后端，使新快照读写逻辑生效。
2. 生成或迁移一个日期的快照。
3. 页面按该历史日期核对总行数、货号搜索、筛选、详情、图片和导出。
4. 与旧表同日期结果抽样比对。
5. 确认后再执行该日期的 `--delete-legacy`。

在未执行 `--delete-legacy` 前，旧行表仍保留，随时可回退到旧读取路径。执行删除后，新结构仍保留完整每日历史；如需回退，应先停止新快照写入并从数据库备份恢复相应旧分区数据。
