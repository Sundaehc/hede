# 补货建议

更新日期：2026-11-14。

## 使用方式

左侧菜单“存 → 补货建议”，地址 `/stock-alerts/replenishment`。查看使用 `product.view`，保存规则使用 `product.manage`，服务端沿用相同权限校验。

选择品牌、供应商、近 7/15/30 天销量及商品关键词，点击查询。默认近 30 天、全部供应商、不抵扣采购在途。输入中的草稿不会改变当前结果、规则范围和分页；查询状态按账户及页面保留。

点击商品行的“设置补货规则”，或筛选供应商后点击“设置供应商规则”，手工填写：

| 规则 | 含义及范围 |
|---|---|
| 供应商交期 | 从下单到到货的天数，0–365 天，首次不预填 |
| 供应商合计起订量 | 当前品牌内该供应商全部商品合计的最低双数，1–1000000 双，首次不预填 |
| 到货后备货天数 | 到货后希望覆盖的销售天数，默认 14 天，可填 1–365 天 |
| 尺码需求配比 | 按该供应商的各尺码组填写整数权重，0–10000；每个已配置尺码组至少一个权重大于 0 |

配比例如 `35:36:37 = 1:2:1`，用于估算目标需求，不强制补货按整包或固定倍数下单。单个尺码留空按 0 保存；整个尺码组未填时允许先保存供应商资料，该组商品进入待完善清单。尺码组新增、删除或改名导致与保存规则不一致时，必须重新核对配比，不沿用不完整规则。

供应商及尺码组选项来自有效商品档案和尺码组管理，不另建供应商档案。同名供应商在不同品牌下分别配置、分别汇总，不跨品牌借用规则。商品未填供应商时先在商品档案补齐。规则保存后所有有查看权限的账户共享；并发保存检查版本，过期保存返回 409，弹窗保留输入。

## 计算口径

1. 销量窗口默认 30 天，包含截止日。有效上市日期位于窗口内的新商品，从上市日开始计算；上市日期未填或格式无效时使用完整窗口。上市日晚于截止日时列为待核对。
2. 日均净销 `D = max(窗口净销量, 0) ÷ 实际统计天数`。预计可售天数 `max(可售库存, 0) ÷ D`，从页面显示的库存快照起算。没有正净销量时显示“无正净销”，不假定无限销量或强制建议补货。
3. 分码日需求 `D_s = D × 当前尺码权重 ÷ 总权重`，是配比估算，并非实际尺码日销。
4. 尺码建议量 `ceil(max(D_s × (交期 + 到货后备货天数) - max(尺码可售库存, 0) - 可抵扣采购在途, 0))`；商品建议量为各尺码建议量合计。使用精确分数比较和向上取整，不把显示时舍入的日均销量用于决策。
5. 当前尺码库存不足以覆盖交期（含恰好用完）时显示“交期内可能缺货”。该风险始终根据现货判断；即使勾选抵扣在途，也保留现货风险提示。
6. 起订量按**当前品牌同一供应商全部有效商品建议合计**判断，在商品搜索、状态筛选及分页前计算。达到起订量显示已达；不足时显示差额，**不把起订量套到每款，也不自动凑单增加商品数量**。存在待完善商品时单独显示数量，有效建议只汇总已能计算的商品。

“建议补货合计”卡片按当前供应商及商品搜索汇总有效建议；“供应商起订汇总”和商品行的起订进度使用整家供应商范围，两者区别在页面明确标注。

列表包含有可售库存、采购在途或近期销售／退回的商品，覆盖有明确零库存快照但近期仍有销量的售罄商品。只有销量、没有对应库存快照明细时列为待核对，不能把缺少库存记录视为零库存。

## 来源与时效

| 内容 | 来源 |
|---|---|
| 商品、供应商、尺码组、上市日期 | 品牌商品信息档案，排除已删除商品，沿用品牌默认条码规则与默认尺码组 |
| 尺码名称、尺码条码及顺序 | `size_groups`、`size_group_items` |
| 可售库存及采购在途 | `jst_full_stock` 最新 `sync_date` 快照的 `available_qty`、`purchase_in_transit_qty` |
| 窗口净销量及退回 | `factory_channel_sales_daily_summaries` 中该品牌 `matched` 商品的 `quantity`、`return_quantity` |
| 销量日期覆盖 | `jst_daily_sales`、`vip_daily_sales`、该品牌渠道日汇总的 `date_marker` |
| 手工规则 | `stock_replenishment_rules`，按品牌及供应商名保存 |

销量截止日取北京时间业务昨日、库存快照前一日、两份日销表最新日期中的最早日期，避免使用晚于库存快照的销售。窗口内逐日核对两份日销及该品牌汇总的日期覆盖；缺日、缺源、商品匹配歧义或尺码无法唯一匹配时不生成确定补货量。全品牌无法唯一匹配的库存编码组单独计数，不任意关联商品。

销量沿用已有渠道日汇总中的聚水潭／唯品去重口径；唯品日销未单列退货。新增商品、修改货号后的历史识别需要等待原有渠道日汇总重建，本页刷新不补算历史来源。

在途只取采购在途，不包含调拨在途及退货在途。当前没有预计到货日期，默认不抵扣；使用者勾选抵扣表示**假设全部采购在途能按时到货**。页面同时保留在途数量和现货风险，供采购核实。

## 运行与验证

后端仍由负责人手动启停。新代码在下一次人工启动时检查并创建 `stock_replenishment_rules` 小型配置表；开发验证不在正式库建表或写入规则。不新增定时任务，不自动生成采购单，不修改商品或库存。

事实读取使用只读、可重复读事务，SQL 超时 25 秒，按品牌、业务日期及销量窗口缓存最长 120 秒，最多 4 项、合计 8 MiB；单个构建锁避免重复查询放大内存。读取既有日汇总及库存聚合，使用流式结果，不扫描原始销售明细。规则每次实时读取，保存及同站点跨标签页通知后重新计算；手动刷新绕过事实缓存。接口响应 `Cache-Control: no-store`。

接口：`GET /stock-alerts/replenishment`、`GET /stock-alerts/replenishment/rules`、`PUT /stock-alerts/replenishment/rules`。

长期前端回归见 [replenishment-page.test.tsx](../frontend/components/stock-alerts/replenishment-page.test.tsx)、菜单及跨标签页通知对应测试。本地后端合成验证放在 `outputs/logs/`，不上传 `backend/tests/`。

验收必须覆盖：

- 同供应商 A、B 两款各建议 35 双，起订量 100 双：显示供应商合计 70 双、还差 30 双，单款不被增加至 100 双；只搜索 A 或翻页，供应商合计仍为 70 双。
- 起订量恰好 70 双时判为已达；另一供应商的数量不能合并凑足。
- 在途默认不抵扣，勾选后按假设扣减，但现货不足交期的风险继续显示。
- 日期缺口、尺码冲突、规则未填、尺码组变化、没有库存记录分别进入待完善，不误报补货 0。
- 零／负净销量不产生需求，零配比尺码不分配需求；精确整数边界不因小数循环舍入多补一双。
- 售罄商品仍参与计算，新品采用实际有效窗口，跨品牌同码歧义不任意匹配。
- 只读账户不能保存，版本冲突保留输入，保存成功后其他同站点标签页重新查询。
