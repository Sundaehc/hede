# 数据库优化总结

日期：2026-07-27

## 1. 优化范围

## 2. 已完成优化

### 2.1 首次统计与清理

已在线执行以下维护，不使用 `VACUUM FULL`，不删除任何业务记录：

| 表 | 执行操作 | 优化前问题 | 结果 |
| --- | --- | --- | --- |
| `vip_daily_sales_2026` | `VACUUM (ANALYZE)` | 死元组约 14.2% | 死元组降为 0 |
| `vip_product_ops_snapshots` | `VACUUM (ANALYZE)` | 死元组约 4.3% | 死元组降为 0 |
| `product_goods_detail_snapshots_2024` | `VACUUM (ANALYZE)` | 死元组约 11.0% | 死元组降为 0 |
| `fine_table_snapshot_rows_2024/2025/2026` | `ANALYZE` | 2024、2025 缺少有效统计信息 | 查询优化器已获得最新行数统计 |

首次维护总耗时约 14 秒。精细表快照最新估算行数分别为 595 万、1105 万、926 万，可避免优化器因统计缺失选错执行计划。

### 2.2 自动维护阈值

已为 8 张高频导入或大体量快照表设置表级自动维护参数：

- `vip_daily_sales_2026`：清理、分析阈值调整为 2% + 1,000 行。
- `vip_product_ops_snapshots`、`product_goods_detail_snapshots_2024/2025/2026`：清理阈值调整为 5% + 5,000 行，分析阈值调整为 2% + 1,000 行。
- `fine_table_snapshot_rows_2024/2025/2026`：清理阈值调整为 5% + 5,000 行，分析阈值调整为 1% + 1,000 行。

默认的分析阈值为 10%，对千万级快照表过于滞后。调整后，导入新快照后可更快刷新统计信息并保持查询计划稳定。

### 2.3 夜间统计维护任务

新增：`HedeDatabaseMaintenance`

- 执行时间：每日 `02:20`
- 脚本：`backend/scripts/maintain_database.py`
- 启动文件：`backend/scripts/maintain_database.cmd`
- 日志：`backend/logs/database_maintenance.log`
- 状态记录：`scheduled_task_statuses`，任务名 `database_maintenance`

任务每日对 14 张大表执行 `ANALYZE`，包含精细表快照、货品表快照、唯品快照、日销、库存、订单、价格和合并商品资料。首次实跑成功，耗时 16.76 秒。

### 2.7 索引复核与冷热分区规划

- `review_database_indexes.py` 会导出索引扫描、约束属性、体积和慢查询摘要，仅输出建议，不执行删索引或重建。首次报告共 `267` 个索引，其中 `43` 个普通索引需要结合 `EXPLAIN (ANALYZE, BUFFERS)` 逐项复核。
- `manage_partition_retention.py` 按近 `24` 个月热数据策略生成分区冷热报告；默认只读，本次识别 `13` 个热分区、`2` 个冷分区，未移动、未删除任何数据。传入 `--apply` 仅为分区写入冷热标记，不会移动表或归档数据。

## 3. 安全边界

本次未执行以下高风险操作：

- 未执行 `VACUUM FULL`、`REINDEX`、删表、删数据或删索引。
- 未删除旧分年表、未删除历史数据、未修改业务接口返回或定时导入来源。
- 分区父表只增加统一查询入口；旧表名、旧代码路径和历史日期查询均继续有效。
- 未直接增加外键或枚举约束，避免历史导入数据导致写入失败。

普通 `VACUUM (ANALYZE)` 与 `ANALYZE` 不使用排他锁，可在系统运行期间执行。夜间任务只更新统计信息，不会重写数据表。

## 4. 后续运行与归档

### 4.1 已完成的结构优化

分区、字段类型治理与索引复核已完成，均采用兼容层和增量切换方式。历史查询无需变更；新报表可优先使用统一父表和 `v_*` 视图。

### 4.2 后续归档执行

近 24 个月分区保留热存储。超过窗口的冷分区在完成备份恢复演练、业务方验收历史查询和读库连接验证前，保持在线只读；不要直接 `DROP`、`DETACH` 或移动任何分区。届时可按表级归档库迁移，并保留兼容视图或 FDW 入口。

### 4.3 查询切换原则

新开发优先：时间条件使用类型化字段/`v_*_normalized` 视图；跨年度查询使用对应统一父表。原始导入层继续使用文本和 `raw_payload`，避免异常 Excel 阻断当天任务。

## 5. 监控项

每日查看以下内容：

1. 计划任务 `HedeDatabaseMaintenance` 是否返回 0。
2. `scheduled_task_statuses` 中 `database_maintenance` 是否为 `success`。
3. `backend/logs/database_maintenance.log` 是否有失败记录。
4. `vip_daily_sales_2026`、货品快照和唯品运营快照的死元组比例是否持续升高。
5. 精细表、货品表历史日期查询是否出现明显变慢。
6. 每月运行 `review_database_indexes.py`，仅对有慢查询证据的普通索引安排 `EXPLAIN (ANALYZE, BUFFERS)` 复核。
7. 每季度运行 `manage_partition_retention.py`；归档操作必须另行审批并完成历史查询验收。
