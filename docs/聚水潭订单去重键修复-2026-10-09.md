# 聚水潭订单去重键修复

## 根因和口径

- 日常滚动窗口导入没有写入 `record_key`，覆盖历史窗口后将已有键替换成空值。
- 唯一约束仍存在，但空键不能阻止重复键写入。
- 2026-10-09 实查近三个月有 81 组、83 条粗粒度疑似多余行，不是早期报告的 82 条。
- 原历史导入九字段指纹也会将 22 组合法明细误判为重复；这些行的内部子订单编号不同，必须保留。
- 新规则保留九字段并增加原始数据中的“子订单编号”／“子订单号”，使用长度前缀和 SHA-256，避免分隔符歧义；数量零与空值区分。

## 修复工具

从仓库根目录运行，默认只读：

```powershell
$env:PYTHONPATH="backend"
D:/python/python.exe -m scripts.backfill_jst_monthly_order_keys --date-start 2026-05-01 --date-end 2026-10-09 --report outputs/db_audit/jst_monthly_order_keys_dry_run_2026-10-09.json
```

确认后添加 `--apply` 执行。仅更新缺失或空白键，不重写已有非空历史键，不删除订单。
执行时锁定目标表防止并发写入，锁等待超过 10 秒取消；新键冲突、备份数量不一致或校验失败时整体回滚。
原键保存到 `jst_monthly_order_key_repairs`，执行报告包含 `run_id`、更新数量及前后覆盖率。

## 回滚原键

暂停相关导入后，把执行报告中的 `run_id` 替换到以下 SQL；先核对备份数量，再在事务内执行。

```sql
BEGIN;
LOCK TABLE public.jst_monthly_orders IN SHARE ROW EXCLUSIVE MODE;
UPDATE public.jst_monthly_orders orders
SET record_key = backup.previous_key
FROM public.jst_monthly_order_key_repairs backup
WHERE backup.run_id = '替换为执行报告中的run_id'
  AND orders.id = backup.record_id
  AND orders.order_time_at = backup.order_time_at
  AND orders.record_key = backup.repaired_key;
COMMIT;
```

回滚不会覆盖此后已改变的键。保留审计备份，避免直接删除合法明细。

## 防止再次缺失

- 日常导入和历史归档共享同一规则。日常导入仅合并完全相同源行，键相同但业务内容不同则取消导入。
- 已有历史的非空旧版键保持兼容；本次工具只补缺失键，不进行全档案重键。
- 新代码需被下一次日常任务加载；若任务使用旧打包程序，必须更新程序后才能避免重新写入空键。
- 审计区分粗粒度疑似重复与含内部子订单编号的真实键冲突，不再建议直接删除粗粒度命中行。
