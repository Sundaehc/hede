# 库存管理业务梳理与实施方案

依据：用户提供的《总体定位与业务主线》材料。核对日期：2026-10-27，北京时间。范围：材料中“存1～存5”，以及与采购、销售、利润板块的交接。

本方案结合当前项目代码和 PostgreSQL 实际表结构、只读统计整理。下文明确区分“已有能力”“存在缺口”“建议建设”；建议表、接口与流程均未实施。本次没有修改业务数据、运行补数、执行建表或重启服务。

## 一、结论与建设边界

**当前可以在已有数据库上建设库存经营管理，但不宜直接把它当成实时仓储系统。**

已有基础包括：商品档案、采购及经营单据、仓库、聚水潭库存报表、日销、售后、历史快照、用户权限、操作日志和定时任务。最适合的建设路径是：

```text
先统一商品 / 尺码 / 仓库身份及库存口径
  → 建可信库存查询与数据质量闸口
  → 建库存健康及核心尺码风险
  → 建补单 / 调拨建议、授权与执行回执
  → 补渠道占用同步、退货处置及盘点闭环
  → 接通原系统实时能力，再评估实时承诺和自动化
```

不建议重建一套采购、销售、仓储和财务交易系统：正式采购、实物出入库、占用释放和结算继续以公司指定的原系统为准，本项目负责归集、判断、协同与追踪。

一期先以**千百度女鞋**试点，但新表均保留品牌与组织范围，不写死只支持女鞋；实际选择哪些仓库、渠道和商品应由业务确认，避免一开始覆盖全量。

## 二、“存”的业务内容

### 存1：库存状态归集——货在哪里、现在能卖多少

需要展示：款式 → 颜色 → 尺码 SKU → 仓库 → 可取得的仓位 / 质量状态。

- 现货、待检、合格、冻结、残次、退货待处理分开展示。
- 采购在途、调拨在途、退货在途分开；展示预计到仓、可靠性和关联单据。
- 源系统可用库存、计算可售和未来可承诺量分开，不用“总库存”替代。
- 每个数能追溯数据源、批次、业务时点、同步时点和计算规则。
- 未取得仓位、质量或订单细分时显示“未提供 / 未确认”，不能猜测为合格可售。

### 存2：渠道占用与库存同步——哪些货已经承诺给谁

- 区分订单占用、渠道专属配额、共享库存和安全缓冲。
- 关联预留、取消释放、发货核销、过期释放及跨仓 / 渠道调整。
- 排查重复占用、重复承诺、库存同步过期、源系统与本地差异。
- 没有统一原子预留能力前，只做查询与预警，不承诺防超卖。

### 存3：库存健康与尺码齐套——还能卖多久、风险在哪里

- 按核心尺码分析可售数量、缺码持续时间和预计覆盖天数。
- 区分现货齐套与含可靠在途的未来齐套，不让未来到货掩盖当前缺码。
- 结合有货期间销量、退货、剩余销售季、供应周期识别缺货与积压。
- 库龄要依赖批次或收货流水；只能看到首单日期时，不能宣称已有真实库存库龄。
- 输出可处理的风险事项，而不只是给商品打一个“正常 / 异常”标签。

### 存4：补单与调拨——补什么、调什么、什么时候做

- 先看可调库存，再看可兑现的在途，再比较采购方案。
- 建议到颜色尺码级，记录依据、需求口径、交期、起订配码、预算和规则版本。
- 授权人可以接受、修改或拒绝，保留理由。
- 补单复用采购下单与交付链；调拨关联原系统调拨单与收货回执。
- 发起建议不是完成采购，建采购单不是已到货，调出不是已调入。

### 存5：退货再售、清货与盘点——该处理什么、如何闭环

- 把退款完成、实物回仓、质检、回架分开。
- 验收后分流至可售、返修、退供、残次或报损，关联实际变更单据。
- 清货方案明确商品范围、渠道、价格底线、负责人、期限及财务复核。
- 盘点保留账面、实盘、差异、复核和原系统调整单；不能直接手改库存余额。
- 追踪净回收、损失及结果成熟度，不把库存下降直接算成利润增长。

## 四、必须优先完善的缺口

### 4.1 主数据：统一款、颜色尺码 SKU 与外部编码

建议的稳定关系：

```text
事业部 / 品牌
  └─ 稳定款式身份
      └─ 商品档案身份（常见为款色，实际粒度需核验）
          └─ 颜色尺码SKU
              ├─ 聚水潭商品编码 / 条码
              ├─ 唯品 goods_id + size_id
              └─ 得物 sku_id / 其他渠道商品编码
```

- 复用 `product_archive_identities`，在它之下补尺码 SKU；不能用跨品牌同名货号直接相连。
- 同一商品多渠道编码采用生效起止时间和来源范围映射；映射变更保留历史。
- 区分外部“款级”“款色级”“尺码SKU级”编码，不能强行把所有来源都落成尺码事实。
- 无唯一匹配、跨品牌冲突、缺尺码时隔离待确认；前缀匹配只能提供候选，不能自动确立长期关系。
- `jst_full_stock` 等表的自增 ID 会随替换变化，不作为业务关联稳定 ID。
- 建稳定款式主数据时，不复用会被标签重建清空的 `product_style_entities`；另建或先改造其生命周期后再迁移。

### 4.2 库存口径：先说明每个数，再计算

当前货品表计算将 `actual_stock_qty + purchase_warehouse_stock_qty` 作为现货，将采购、调拨、退货在途相加为在途，再将现货加在途作为整体库存。这个口径可以保留为既有报表展示，但在确认源字段是否重叠之前，**不能当作本方案的可信可售或实时可承诺量**。

建议分别输出：

| 名称 | 建议定义 | 前提 |
| --- | --- | --- |
| 实物在仓 | 截止时点实际位于仓内的数量，按质量状态拆分 | 原系统仓库 / 状态数量互斥并对账。 |
| 合格可售基础量 | 合格且允许当前渠道销售的现货，排除待检、冻结、残次等 | 质量状态来源明确；未知状态不能当合格。 |
| 源系统可用数 | 原系统给出的 `available_qty`，原样保留包括负数 | 明确它是否已扣订单占用、冻结和渠道分配。 |
| 即时可承诺量 | 在确认互斥口径后，从合格可售基础量扣有效订单占用、专属配额 / 保护量及安全缓冲 | 不能再次扣减已包含在源可用数中的同一项。 |
| 预计日期可供量 | 即时可承诺量 + 截止该日期可靠到货并完成QC和入库的数量 - 该日期前新增承诺 | 没有可靠ETA或QC缓冲的在途不能默认纳入。 |
| 库存资金占用估计 | 约定库存范围 × 财务认可的成本口径 | 当前档案成本只是参考，不替代实际存货计价或已入账减值。 |

仅展示非负承诺能力时可以给出 `max(0, 可承诺量)`，但必须另列负余额 / 超占异常，不能把负数静默抹成0。不可用状态和数量缺失要显示未知，不用默认0假装完整。

### 4.3 同步可信度：成功、时效、完整性分开

- 复用现有任务日志，另补可关联到具体事实的同步批次；记录源系统、文件校验和或游标、导出 / 查询时点、同步时点、覆盖仓库、行数、失败行、状态和校验结果。
- `sync_date` 只是导入日；行上的 `inventory_updated_at` 可能是最后库存变动时间，当前有大量早于导入日的值，不能据此判断整份文件过期。
- 检查文件修改时间、导出时间和实际覆盖范围，防止“今天重复导入旧文件”被当作今天库存。
- 全量导入先写暂存、校验，再原子切换可见成功批次；空文件、解析错误和异常数量不能覆盖上一次可信批次。
- 当前全量库存入口在替换事务结束后才判断 `imported == 0`，空数据异常可能发生在清空已提交之后；应把有效数据校验移到发布之前。
- 未成功批次不参与余额；重放相同文件 / 事件必须幂等。部分成功不得伪装成全仓完整。
- 关键映射、库存质量或同步时效不达标时暂停对应建议，并显示原因、责任人和重跑入口。

### 4.4 订单、在途和退货要有稳定的行级关联

- 当前 `jst_monthly_orders` 是滚动窗口替换，自增 ID 不稳定；其 `record_key` 还包含数量和状态，不能直接拿来作永久订单行 ID。
- 应取得原系统稳定订单行 / 子单、采购行、入库行、退货行标识；若源不提供，先约定业务组合键和冲突处理，不做模糊自动绑定。
- 一笔退货可能拆批、拆码、部分退款或部分回仓，必须支持分次回执，不以订单总退货量代替每一件状态。
- 在途需要明确来源单据行、数量、已收量、取消量、预计到仓、可靠性和目标仓；现有汇总在途不能直接提供这些信息。
- 只凭日报状态无法重建实时预留、释放、核销。接入源系统事件或可验证的增量接口前，先做非实时核对。

### 4.5 库存健康与经营动作的缺口

- 当前断码规则基于存在的尺码键和固定阈值，未出现的必备尺码可能未进入计算；应从该商品有效尺码组生成完整尺码全集，区分“0库存”和“数据未提供”。
- 当前齐套判断可包含在途数量，可能掩盖现货缺码；新增现货齐套、未来齐套两个指标。
- 补货量不能只按过去尺码销量比例分配：还应考虑有货时长、交期、起订量、配码、季末、退货及预算。
- 未取得批次或完整收发存流水前，真实库龄和精确有货小时不可得；展示代理指标和适用限制。
- “经营历程完成 / 未完成”当前主要按明细价格 / 金额完整程度等计算，**不是采购交付完成、QC通过或库存入账的状态**，新流程不能复用此含义。
- 现有调拨在仓库汇总中体现两端增减，但尚不是“申请 → 调出 → 在途 → 调入 → 差异”的执行链。

## 五、数据库如何落地

以下表名为**建议设计，当前未创建**。不要求一次建完，应按阶段和源数据可得性选择。关键业务键、数量、状态、时间及关联不宜继续全部塞入 `extra_fields`。

### 5.1 第一期：主数据、可信批次与健康分析

| 建议对象 | 核心字段 / 关联 | 用途 |
| --- | --- | --- |
| `product_styles` | `id`、品牌 / 组织、内部款式编码、生命周期、创建 / 停用时间 | 独立稳定款身份；不受标签重建影响。 |
| `product_skus` | `id`、`style_id`、`product_identity_id`、颜色、标准尺码、状态、计量单位 | 颜色尺码交易SKU；按实际业务定义唯一性，不把整个鞋码范围当SKU。 |
| `product_sku_aliases` | 源系统、品牌 / 店铺范围、外部商品 / 尺码标识、条码、`sku_id`、生效时间、确认状态 | 跨系统尺码编码映射，保留历史；款级编码另按档案 / 款式关联。 |
| `warehouse_source_mappings` | 源系统、外部仓库代码 / 名称、内部 `warehouse_id`、生效区间 | 统一外部仓库身份；不把组织名称当成已确认的实物仓。 |
| `stock_sync_batches` | 来源、校验和 / 游标、业务时点、同步时间、覆盖范围、数据模式、行数、质量结果、发布状态、替代批次 | 保留原始来源和批次生命周期；重复导入可识别。 |
| `stock_position_snapshots` | `batch_id`、品牌、`sku_id`、仓库、可选位置、质量 / 状态、数量、源可用数、源行引用 | 保存同一来源同一时点的库存事实；查询只取各权威范围的已发布批次，不混加重复来源。 |
| `stock_policy_versions` | 品牌 / 商品 / 渠道范围、版本、生效日期、阈值、核心尺码 / 配比、供货与季节规则、批准人 | 统一库存、缺码及建议口径；版本不可原地覆盖。 |
| `stock_health_daily`（有性能需要再落表） | 日期、`sku_id`、仓库 / 渠道范围、覆盖天数、风险、数据质量、规则版本和输入批次 | 可先计算查询，再按性能需求增量预计算；不必立即增加所有派生表。 |

一期暂不具备仓位、质量细分时，可以保存“来源报表可用数”和未知状态，但页面须注明“报表口径”，不能因此启用即时承诺或自动下单。

### 5.2 第二期：建议、授权、执行与复核

| 建议对象 | 核心内容 |
| --- | --- |
| `stock_action_cases` | 补货、调拨、清货、停采、取消未交、停售、退供等行动；范围、负责人、期限、优先级、当前状态、幂等业务标识。不同动作不混为一个“清仓”按钮。 |
| `stock_action_lines` | SKU、仓库 / 渠道、建议数量、人工确认数量、来源采购 / 订单行；支持一行动多尺码明细。 |
| `stock_action_decisions` | 接受 / 修改 / 拒绝、理由、申请和批准人、时间、依据批次、规则版本、当时价格与成本、约束及不确定性快照。 |
| `stock_action_receipts` | 原系统类型、单据 / 行号、执行状态、数量、时间、证据、错误和部分完成结果；同一外部回执不可重复累计。 |
| 复核记录 | 可作为行动的子记录，保存2～3天执行检查、到货后和售后成熟后的经营复核、实际结果与归因限制。多次复核不得覆盖旧结论。 |

复用 `auth_users` 和 `operation_logs`，补操作级权限、品牌 / 仓库数据范围、申请与批准分离以及异常升级。经手人文本保留为历史展示，不直接作为授权用户身份。

### 5.3 后续：接通源系统后再补执行事实

| 建议对象 | 启用条件与内容 |
| --- | --- |
| 稳定外部单据关联 | 订单行、采购行、入库行和售后行的源ID及本地身份；不依赖滚动替换表自增ID。 |
| `stock_inbound_schedules` | 可追溯到采购 / 调拨 / 退货行的分批到货数量、ETA、可靠性、QC缓冲、取消和已收量。 |
| `stock_reservation_events` | 读取原系统稳定预留事件，区分预留 / 释放 / 核销、订单行、渠道、仓库、数量、源版本和时间。 |
| `stock_channel_quotas` | 仅当确有专属渠道配额规则时增加，保留共享池 / 专属额度、有效期、审批和变更事件。 |
| 退货验收事实 | 原订单 / 售后行、分次回仓、尺码、质量等级、验收与回架 / 返修 / 退供 / 报损；关联原系统库存变更单。 |
| 盘点与差异 | 盘点范围、截止批次、账面、实盘、差异、复核及原系统调整单，保留反向更正。 |
| 批次 / 库龄层 | 取得可靠收货批次和出入库消耗规则后建设；只知道最早入库日不足以确认当前剩余库存年龄。 |
| 镜像实物流水 | 只有获得稳定事件ID、方向、发生时点和可校验期初才建设；用于对账，不在未获授权时接管源库存账。 |

### 5.4 键、约束和存储原则

- 稳定身份使用主键；外部别名按“来源 + 明确范围 + 外部标识 + 生效区间”防冲突。编码更名或重用不覆盖历史映射。
- 事实表按批次与实际粒度建立唯一约束；仓库、位置、状态存在空值时明确空值去重语义，不依赖普通唯一索引自动阻止所有重复。
- 保留业务发生时间、源查询 / 导出时点、到库同步时间和映射生效时间；新事件用 `timestamptz`，历史无时区字段先核实实际时区再迁移。
- 数量计量单位需明确为双、只、件或其他；源报表为整数不代表所有经营明细都能直接转整数，转换需业务确认并可审计。
- 单据事实、批次快照、当前余额、派生指标分开。当前余额可以由最新可信批次的视图或读模型提供，不维护两套可手工修改的真余额。
- 质量问题可复用 `data_quality_issues` 并补来源批次 / 对象字段，或在现有结构无法表达时单独扩展；不把数据错误静默吞入JSON。
- 决策依据需要冻结实际字段值、源标识与校验和，不能只保存以后会被替换的行ID或会变化的文件路径。

## 六、计算规则与数据闸口

### 6.1 需求与补货

建议规则必须先由商品、运营和财务确认，下面是实现结构，不是已经批准的经营公式。

```text
参考日需求 = 可比较窗口内的有效销售需求 / 同窗口有效有货天数

保护期 = 评估周期 + 可靠采购提前期 + QC/入库缓冲

保护期净供给 = 合格现货 - 已有有效承诺
               + 保护期内可靠可用到货

基础补货缺口 = max(0, 保护期预测新增需求 + 安全量 - 保护期净供给)

建议采购 = 在缺口基础上应用最小起订/配码、资金、剩余销售季、
           价格与贡献、已有未交采购、可调拨余量等限制后的方案
```

其中“新增需求”必须排除已经计入有效承诺的订单，避免再把占用重复扣一次。预计退货只有质量、数量和时点可靠时才能纳入未来供给；待退货不能当作现货。

各统计口径分别校验守恒：实物余额满足“期初 + 实际入库 - 实际出库 ± 经批准调整 = 期末”；预留余额满足“期初预留 + 新预留 - 释放 - 发货核销 = 期末预留”。占用只改变可用，不单独减少实物；发货核销时不能对同一数量重复扣实物和可用。跨仓调拨要以调出、在途、调入状态分段对账，不在调出后立刻假定目标仓已收到。

现阶段若只有每天一次库存快照，只能计算“按日快照估计的有货天数”，不能精确计算实际有货小时；历史缺快照也不能默认当天缺货。没有可比有货样本时显示证据不足，不把低销量直接判成需求低。

### 6.2 核心尺码与库存健康

- 商品有效尺码组先生成应有尺码全集，核心尺码和权重由品类 / 款式及业务确认，不用所有商品同一固定配比。
- 当前核心尺码可得率以合格现货扣有效承诺后计算；未来可得率独立纳入可靠到货。
- 可售覆盖天数使用明确需求分母；分母为0或不足时显示无法估计，不显示无穷大或机械当正常。
- 同时看缺码、长库龄、过季、库存集中、在途延期、负可用、待检积压和高退货，不只追求不断货。
- 清货与补货冲突检查按“同SKU + 仓库 / 渠道范围 + 质量状态 + 时间条件”判断；正常补码和残次清理可以并存。

### 6.3 必须具备的闸口

| 闸口 | 不通过时的行为 |
| --- | --- |
| SKU / 品牌 / 仓库唯一映射 | 受影响行隔离，保留原文；暂停该对象的数量建议。 |
| 源文件完整、业务时点可信、批次发布成功 | 继续展示上次可信值和过期提示，不自动将失败批次发布。 |
| 库存状态定义与数量对账 | 暂停可承诺量，允许展示明确标记的来源报表值。 |
| 渠道占用与配额不重复扣减 | 暂停跨渠道承诺和自动分配，不用估算数当已预留。 |
| 在途有可靠ETA、数量和收货去重 | 不确定在途只展示，不计入对应日期保证供给。 |
| 销售与退货口径可比且跨渠道排重 | 暂停依赖该需求的补货计算，保留人工判断入口。 |
| 交期、起订配码、预算和预计贡献可核实 | 根据缺失影响降级或阻断采购建议；数量风险可继续展示，不伪造利润。 |
| 权限、理由、单据回执与重复检查 | 不允许越权执行；失败进入异常队列，支持按幂等键重跑。 |

## 七、建议实施步骤

### 第0步：确认原系统与责任口径

1. 由仓储、采购、运营、财务确认各数据的权威系统和维护人。
2. 选定女鞋试点的仓库、渠道、时间窗口和商品范围。
3. 确认实际 / 可用 / 订单占用 / 各仓 / 在途字段含义，特别是是否重叠。
4. 确认批次时效、QC、核心尺码、起订配码、销售季、预算和批准权限。
5. 核实聚水潭及其他原系统可提供哪些API、事件、单据行及状态，不能先假定接口都存在。

**交付与验收：**一份签字或授权确认的口径 / 数据字典、试点范围、责任表和缺源清单。缺口先确定来源和限制，不补造事实。

### 第1步：修同步与主数据，先不改业务余额

1. 预览并处理库存汇总日期空值，保证当前业务日可追溯；历史不能直接套当前年份。
2. 调整全量导入为暂存校验后发布，防止空批次清空当前库存。
3. 补来源批次、文件版本、范围、完整性和源查询时点。
4. 建稳定款 / 尺码SKU与跨系统、仓库映射，空值和歧义进入待确认队列。
5. 对同一原始文件重放、失败后重试、重复行和跨源冲突做验证。

**交付与验收：**原始来源可以定位，已发布批次可回溯，相同输入不重复累计，失败仍可读上一可信批次；试点全部有效库存要么映射成功，要么明确隔离，不能静默漏行。

### 第2步：上线库存总览与单款库存明细

1. 增加“库存管理”入口，在同一系统复用商品图片、档案和品牌配置。
2. 建按款汇总、颜色尺码下钻、仓库 / 状态筛选和数据时效提示。
3. 明确展示实物、源可用、订单占用、待检、各类在途及未知项。
4. 对照源系统报表抽样核对，解释与现有经营历程收发存的差异。
5. 用最新成功批次的SQL视图或读模型服务页面，不在浏览器对所有库存做聚合。

**交付与验收：**款色码仓汇总与源数据在约定容差内一致；待检不显示为合格可售，在途不显示为现货，无数据不当0。

### 第3步：上线库存健康和核心尺码风险

1. 核准并版本化核心尺码 / 安全量 / 需求窗口 / 季节等规则。
2. 从现有两类日销及库存历史算日级趋势，先处理重复渠道和退货口径。
3. 区分现货缺码、未来到货补足和过季积压。
4. 建负可用、未映射、日期过期、来源差异和待处理风险列表。
5. 每条风险显示触发依据、规则版本、覆盖范围及缺失信息。

**交付与验收：**不存在的核心尺码能被识别；在途不能掩盖当前缺码；旧数据触发暂停或降级；不能识别真实库龄时有明确限制提示。

### 第4步：补单 / 调拨行动闭环

1. 在风险页发起建议，冻结输入数据、规则和不确定性。
2. 支持接受 / 修改 / 拒绝、审批、负责人、时限和待办。
3. 补单关联原系统或现有采购单；明确其何时成为正式采购事实。
4. 调拨记录调出、在途、调入和差异，禁止同一回执重复累计。
5. 2～3天先查响应与执行；到货和销售观察期达到后再复核缺码、积压、资金和贡献。

**交付与验收：**至少覆盖正常、部分完成、取消、拒绝、超期、并发审批和重复回执样例；所有正式动作有人确认、有单据、有结果。

### 第5步：接入占用事件与渠道分配

1. 先镜像、核对原系统占用，不先发明第二份可修改占用账。
2. 取得稳定事件ID、版本、取消、发货和重试语义；处理乱序和晚到。
3. 确有专属配额业务时才增加配额，说明它与订单占用的交集及扣减规则。
4. 只有原系统提供或经授权建设统一原子预留后，才开放实时可承诺量。
5. 若本地成为预留权威，须使用事务锁 / 版本控制、唯一幂等键、双边调拨及外部发送队列，并与旧机制完成切换，不能两套同时承诺。

**交付与验收：**支付 / 取消 / 部分发货 / 重复事件 / 乱序 / 断网恢复后数量守恒，不重复扣减；仅定时报表方案明确不保证防超卖。

### 第6步：退货、清货、盘点与成熟复核

1. 建售后申请、实物回仓、QC、回架 / 处置关联，支持部分和多次处理。
2. 清货、退供、报损方案走价格、权限和财务复核，关联销售或库存单据。
3. 盘点先冻结账面截止点，记录实盘差异，再以审批后调整单更正。
4. 取得可靠收发存和批次后，完善真实库龄、减值及资金占用分析。
5. 用成熟销售 / 售后窗口检查净回收与损失，不把短期库存下降等同已实现收益。

**交付与验收：**退款未回仓不增加库存；回仓待检不直接可售；盘点差异能追到调整单；清货与补货的合理并存和真正冲突可解释。

## 八、页面和接口建议

建议只增加一个“库存管理”模块和角色视图，不为存1～存5各重建一套应用。

| 页面 | 重点内容 |
| --- | --- |
| 库存总览 | 现货、源可用、占用、待检、在途、数据质量；按品牌 / 仓库 / 状态筛选。 |
| 单款库存 | 颜色尺码矩阵、核心尺码、渠道供给、历史趋势、来源与关联单据。 |
| 库存健康 | 缺码、预计缺货、积压、过季、负可用、待检滞留及同步异常。 |
| 补停清调工作台 | 建议依据、授权、负责人、期限、采购 / 调拨 / 清货回执和复核。 |
| 退货与差异队列 | 待回仓、待检、待回架、退供、报损、盘点差异及处理记录。 |

建议只读接口先做 `GET /stock/overview`、`/stock/positions`、`/stock/products/{identity_id}`、`/stock/health`、`/stock/sync-batches`；行动再提供 `POST /stock/actions`、独立决定 / 回执接口。接口按稳定ID、数据范围、业务时点和批次查询，返回数据质量及口径版本。

这些都是新接口规划。现有 `/warehouses/{id}/inventory` 保持原有经营单据收发存口径，不能不通知用户就替换其含义。

## 九、性能与迁移安排

- 只读统计显示当前经营明细约371万行、尺码快照约1,516万行、汇总快照约297万行（均为数据库估算）；不要让每次分页跨全部历史重算。
- 按“批次 + 品牌 + 仓库 + SKU”等实际筛选建立组合索引，详情按SKU和时间检索；索引以真实执行计划验证，不先盲目增加每列索引。
- 大事件 / 快照表按实际增速选择月或年分区，不预建大量空表；当前读模型与历史归档分开。
- 原始文件可以按批准保留期保存为受控附件 / 对象存储，数据库保存校验和及引用；稳定关联、关键查询字段用类型化列，非关键扩展再用JSONB。
- 历史导入分批、可断点、单批幂等；映射预加载，批量暂存 / COPY，避免逐行查商品。对重放和更正保存批次关系。
- 新增表和索引通过受控迁移和独立SQL文件交付，不把长时间回填放进HTTP启动；先备份、预览、影子运行，再灰度试点。
- 原有表和接口先不破坏，使用双读核对结果而不是双写两套权威余额；可回退到旧页面并停用新建议。
- 验证从纯规则单元测试开始，再用临时数据库测试批次切换、幂等、部分回执、并发和乱序；生产只读抽样对账。故障演练覆盖空文件、源数据过期、缺尺码、重复事件、取消后晚到发货和退款未回仓，不在业务库里制造测试交易。
- 现有每日任务可作为离线分析起点；分钟级承诺需要原系统增量接口或事件，不是把每日Excel任务频率调高就足够。

## 十、优先级与暂缓范围

| 优先级 | 应做内容 |
| --- | --- |
| P0：可信度基础 | 库存日期、空批次发布保护、唯一SKU / 仓库映射、源字段口径、同步时效、未知值与重复来源。 |
| P1：业务先用起来 | 库存总览、款色码仓明细、核心尺码和健康风险、规则版本、负责人和人工行动闭环。 |
| P2：接通执行链 | 在途行级计划、原系统回执、占用事件 / 配额、退货验收、调拨和盘点状态链。 |
| P3：经营深化 | 完整流水与批次库龄、财务认可的库存价值 / 减值、多渠道实时承诺和成熟结果复核。 |

一期暂缓：自动采购下单、自动清仓降价、自建全功能WMS、把预测库存写回实物账、AI直接改数量 / 金额、自动计算或发放奖金。

**建议首批交付：女鞋库存可信视图 + 核心尺码风险 + 补单 / 调拨行动与回执。** 缺少实时接口时仍可获得经营价值，但必须明确数据时点、不确定性和非实时边界。

## 十一、需要业务补充确认的资料

1. 聚水潭、管家婆、唯品、得物等各系统的权威范围，是否有OMS / WMS接口和事件权限。
2. 试点仓库与源仓名称的真实含义，颜色尺码编码规则、单位、条码以及一货多码情况。
3. 实际库存、进货仓、可用、占用、待检、各类在途之间是否互斥；原系统如何防超卖。
4. 采购单 / 入库单 / 订单 / 售后行稳定ID，部分取消、分批收货、换码和重复导出规则。
5. 核心尺码、供应提前期、起订配码、季节截止、清货价格底线和资金预算。
6. 退货质检分级、回架 / 退供 / 报损流程及责任人，盘点和调账权限。
7. 财务认可的存货成本、未来净回收、减值、贡献和成熟观察口径。
8. 数据过期阈值、异常响应期限、业务批准人、可见范围和复核周期。

这些是启动前需要明确的条件，不代表当前项目必须重新手工录入全部资料；能从原系统取得的应自动读取，只让人确认例外和决策。
