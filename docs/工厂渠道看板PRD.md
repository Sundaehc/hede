## 1. 背景与目标

### 1.1 建设背景

商品经营人员需要按季节观察各工厂的款数、销量及渠道结构，判断工厂商品更适合传统赛道、直播赛道还是清仓赛道。此前该分析依赖人工从 Excel 透视表汇总，存在口径不统一、筛选不便、历史年份查询慢和数据追溯困难的问题。

### 1.2 产品目标

1. 在系统内按品牌、季节、工厂统一展示款数、销量汇总及渠道占比。
2. 明确传统赛道、直播赛道、清仓的统一计算口径。
3. 支持销售年份、商品年份、日期范围和工厂名称筛选。
4. 以春夏款、秋冬款两张表展示，便于与原 Excel 分析习惯对应。
5. 复用商品档案、历史销量和日销数据，不新增人工维护销量数据。

### 1.3 非目标

1. 不替代货品表的 SKU/尺码库存、补单、断码等明细分析。
2. 不用于自动评定工厂好坏或自动生成采购决策。
3. 不在本期展示销售额、利润、退货率、库存周转或平台店铺明细。
4. 不将商品上的“清仓”人工标签作为销量渠道划分依据。

## 2. 用户与权限

| 用户 | 使用目的 | 权限 |
| --- | --- | --- |
| 超级管理员 | 查看所有品牌、核对数据口径 | 可访问 |
| 商品部 | 工厂选款、季节规划、渠道结构分析 | 可访问 |
| 开发部 | 商品开发与工厂协同分析 | 可访问 |
| 其他部门 | 当前不开放 | 不可见导航且接口返回无权限 |

### 2.1 权限规则

1. 看板位于左侧导航“商品档案”分组，名称为“工厂渠道看板”。
2. 与商品货品表保持一致：仅超级管理员、商品部、开发部可访问。
3. 前端负责隐藏导航；后端必须校验部门/角色，禁止通过直接访问接口绕过权限。
4. 初版为只读看板，不产生编辑、导入、导出或操作日志。

## 3. 信息架构与页面布局

```text
商品档案
  ├── 商品信息档案
  ├── 商品精细表
  ├── 商品货品表
  └── 工厂渠道看板
        ├── 筛选区
        ├── 核心指标卡
        ├── 春夏款工厂表
        └── 秋冬款工厂表
```

### 3.1 页面结构

| 区域 | 内容 | 交互要求 |
| --- | --- | --- |
| 页面头部 | 标题“工厂销量与渠道占比”、销售数据截至日期 | 截至日期显示当前结果中最大销售日期。 |
| 筛选区 | 品牌、销售年份、商品年份、工厂名称、开始日期、结束日期、重置、刷新 | 筛选条件应可组合、可清空。 |
| 指标卡 | 工厂数、季款数、销量汇总、传统赛道占比、直播/清仓占比 | 工厂名称筛选后实时重算，无需再请求接口。 |
| 季节表 | 春夏款、秋冬款分别展示工厂经营数据 | 默认按销量汇总降序。 |

### 3.2 响应式展示

1. 常规屏幕显示：工厂、款数、销量汇总、渠道占比。
2. 渠道占比使用传统/直播/清仓三段色条和百分比文本展示。
3. 超宽屏额外展示传统赛道、直播赛道、清仓的销量绝对值。
4. 工厂名称优先保证完整显示，可自动换行；页面不应要求横向滚动查看基础字段。
5. 工厂名称或工厂代码筛选在浏览器本地即时生效，筛选结果同步影响两张季节表和顶部指标。

## 4. 筛选功能

| 筛选项 | 数据来源 | 规则 |
| --- | --- | --- |
| 品牌 | 四品牌商品档案 | 支持千百度男鞋、千百度女鞋、烟斗、伊伴；默认千百度男鞋。 |
| 销售年份 | 有数据的年度销量表 | 默认自动选择最新可用销售年份。 |
| 商品年份 | 商品档案 `year` | 仅限制参与款数和销量归属的商品，不改变销售年份。 |
| 工厂名称 | 看板返回结果 | 支持工厂名称或工厂代码的包含匹配；不重新请求接口。 |
| 开始日期 | 所选销售年份的销量日期 | 与结束日期一起限制销量统计范围。 |
| 结束日期 | 所选销售年份的销量日期 | 不得早于开始日期。 |
| 重置 | 页面状态 | 清空销售年份、商品年份、工厂名称和日期范围，恢复默认查询。 |
| 刷新 | 后端 API | 按当前筛选条件重新查询，用于获取最新导入数据。 |

## 5. 指标与计算口径

### 5.1 工厂与款数

| 指标 | 计算口径 |
| --- | --- |
| 工厂 | 商品档案 `supplier_name`，为空时归为“未维护工厂”。 |
| 工厂代码 | 按工厂名称关联 `suppliers.factory_code`；未匹配时为空。 |
| 季节 | 商品档案 `season_category` 含春/夏归为春夏款，含秋/冬归为秋冬款；未维护季节不进入两张季节表。 |
| 款数/季款数 | 对商品 `original_sku` 去除末尾两位颜色编码后去重；同款不同颜色仅计 1 款。 |

### 5.2 销量

1. 统计单位为销量件数，不含销售额。
2. 历史年份优先使用对应年度的历史销量表，避免与部分日销回填重复累计。
3. 当前年或没有历史销量表的年份合并聚水潭日销与唯品日销。
4. 聚水潭使用净销量 `net_sales_quantity`；唯品使用 `sales_quantity`。
5. 当聚水潭渠道识别为唯品、且同一商品同日存在唯品日销记录时，以唯品日销为准，聚水潭该部分不重复累计。
6. 货号匹配优先按销售货号以商品货号开头关联，无法匹配时在款号唯一的情况下按款号关联。

### 5.3 渠道赛道

渠道优先读取店铺渠道映射表；无映射时按原始渠道名称关键词兜底。

| 赛道 | 定义 | 包含示例 |
| --- | --- | --- |
| 清仓 | 原始渠道名称含“清仓”，或映射结果为“达播清仓”“拼多多清仓” | 达播清仓、拼多多清仓。 |
| 直播赛道 | 非清仓前提下，映射/渠道结果为“直播赛道” | 直播店、达人直播等。 |
| 传统赛道 | 总销量扣除直播赛道销量和清仓销量后的其余销量 | 唯品、天猫、得物、拼多多、京东、商品卡、总部、其他非清仓渠道。 |

渠道归类优先级为：**清仓 > 直播 > 传统**。因此直播清仓订单只计入清仓，不重复计入直播。

### 5.4 占比计算

```text
工厂销量汇总 = 传统赛道销量 + 直播赛道销量 + 清仓销量
传统赛道占比 = 传统赛道销量 / 工厂销量汇总 × 100%
直播赛道占比 = 直播赛道销量 / 工厂销量汇总 × 100%
清仓占比 = 清仓销量 / 工厂销量汇总 × 100%
```

当工厂销量汇总为 0 时，三类占比均显示 `0.0%`，不得显示 NaN、Infinity 或空白。

## 6. 数据源与刷新

### 6.1 数据源

| 数据 | 表/来源 | 字段/用途 |
| --- | --- | --- |
| 商品档案 | `cbanner_mens_products`、`cbanner_womens_products`、`yandou_products`、`eblan_products` | `sku`、`original_sku`、`supplier_name`、`season_category`、`year`。 |
| 工厂代码 | `suppliers` | `name` 对应 `factory_code`。 |
| 2024 历史销量 | `product_goods_historical_sales_2024` | 销售日期、货号、款号、渠道、销量。 |
| 2025 历史销量 | `product_goods_historical_sales_2025` | 销售日期、货号、款号、渠道、销量。 |
| 年度聚水潭日销 | `jst_daily_sales_YYYY` | `product_code`、`style_code`、`channel`、`sales_date`、`net_sales_quantity`。 |
| 年度唯品日销 | `vip_daily_sales_YYYY` | `goods_code`、`style_code`、`sales_date`、`sales_quantity`。 |
| 店铺渠道映射 | `product_goods_shop_channel_mappings` | 按品牌维护 `shop_name → channel` 映射。 |

### 6.2 数据更新

1. 商品档案由每日商品同步任务更新，影响工厂、季节、款号和商品年份归属。
2. 日销数据由日报导入任务写入年度日销表；历史销量由固定历史工作簿回填后不主动更新。
3. 看板不维护独立结果表，查询时读取数据库实时聚合；服务端缓存有效期为 5 分钟。
4. 商品、渠道映射或销量导入完成后，应清理货品表/看板缓存；最长 5 分钟后自动刷新缓存。

## 7. 功能需求

### 7.1 核心指标

| 指标卡 | 说明 |
| --- | --- |
| 工厂数 | 当前筛选结果中不同“工厂名称 + 工厂代码”的数量。 |
| 季款数 | 春夏和秋冬表中符合条件款号数之和。 |
| 销量汇总 | 当前筛选结果的总销量。 |
| 传统赛道 | 传统赛道占比及对应销量。 |
| 直播 / 清仓 | 直播赛道占比、清仓占比及对应销量。 |

### 7.2 工厂季节表

| 字段 | 说明 |
| --- | --- |
| 工厂 | 工厂名称；第二行展示工厂代码（如有）。 |
| 款数 | 当前季节、筛选条件下的去色款号数量。 |
| 销量汇总 | 该工厂该季节的销量总和。 |
| 传统赛道 | 超宽屏展示传统销量；常规屏在渠道占比提示中可查看。 |
| 直播赛道 | 超宽屏展示直播销量；常规屏在渠道占比提示中可查看。 |
| 清仓 | 超宽屏展示清仓销量；常规屏在渠道占比提示中可查看。 |
| 渠道占比 | 三段色条：蓝色传统、紫色直播、橙色清仓；同时显示各赛道百分比。 |

### 7.3 异常与空状态

1. 无销量数据时，顶部显示“暂无销售数据”，季节表显示“当前筛选条件下暂无数据”。
2. 开始日期晚于结束日期时，接口提示“开始日期不能晚于结束日期”。
3. 无权限用户访问页面或接口时，返回 `403`，提示仅商品部、开发部和超级管理员可访问。
4. 加载失败时显示错误提示与刷新入口；不得保留错误请求的旧筛选结果作为新结果。

## 8. 接口需求

### 8.1 查询接口

`GET /api/product-goods/factory-channel-dashboard`

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `brand` | string | 是 | 品牌编码：`cbanner_mens`、`cbanner_womens`、`yandou`、`eblan`。 |
| `sales_year` | integer | 否 | 销售年份；为空时选择最新可用年份。 |
| `product_year` | string | 否 | 商品档案年份筛选。 |
| `date_start` | date | 否 | 销量开始日期，ISO `YYYY-MM-DD`。 |
| `date_end` | date | 否 | 销量结束日期，ISO `YYYY-MM-DD`。 |

返回内容包括：品牌、选中年份、可选年份、最新销售日期、顶部汇总、春夏/秋冬工厂列表及每个工厂的款数、三类销量和三类占比。

### 8.2 性能要求

1. 历史销量表必须在数据库端按货号、款号、渠道汇总，禁止按日明细全量传到应用层后再计算。
2. 默认品牌首次查询目标：P95 不高于 2 秒；同条件缓存命中目标不高于 200 毫秒。
3. 切换 2024/2025 历史年份的实测基准：千百度男鞋约 0.7–0.8 秒，千百度女鞋 2025 约 1.5 秒。
4. 工厂名称筛选在前端本地执行，目标交互反馈不高于 100 毫秒。

## 9. 验收标准

1. 具备权限的用户可从左侧导航打开看板；无权限用户看不到入口且不能直接请求接口。
2. 品牌、销售年份、商品年份、日期范围、工厂名称筛选均可用，重置后恢复默认条件。
3. 页面同时展示春夏款和秋冬款两张工厂表，默认按销量从高到低排序。
4. 每行满足：`销量汇总 = 传统销量 + 直播销量 + 清仓销量`；三项占比之和允许因四舍五入产生不超过 `0.1%` 的误差。
5. 传统赛道必须包含直播和清仓之外的所有渠道；清仓优先于直播归类。
6. 工厂名称完整可见，常规屏不需要横向滚动即可看到工厂、款数、销量和渠道占比。
7. 2024/2025 年份切换符合性能要求，且优化前后同筛选条件下销量汇总一致。
8. 数据源缺失、无匹配商品或未维护季节时，不得影响其他已匹配工厂的统计结果。

## 10. 后续迭代

| 优先级 | 能力 | 说明 |
| --- | --- | --- |
| P1 | 导出 | 按当前筛选导出春夏/秋冬工厂明细及渠道销量、占比。 |
| P1 | 趋势分析 | 展示工厂按月销量与三赛道占比变化。 |

| P2 | 预警 | 对直播/清仓占比突增、销量异常下滑、季款销量过低等情况提示。 |
