# 定时任务数据来源与关联表说明

核对日期：2026-10-27。以下时间均为服务器北京时间（UTC+8）。

本说明根据服务器实际 Windows 计划任务、当前 `backend/config.py` 加载的路径配置、任务入口和数据库写入代码整理，不以旧文档中的时间或任务历史列表作为现行配置。

## 一、范围与阅读方式

- 本项目相关已注册任务共 **25 项：23 项启用、2 项禁用**；启用任务中，20 项每日执行，3 项按周或月执行。
- “计划时间”是触发时间，不是数据已经更新完成的时间。重复窗口内通常每 30 分钟触发一次；支持业务状态的任务当天成功后会跳过。
- 数据来源多数是其他系统、采集工具或人工放入共享目录的 Excel。本项目负责读取和入库，不代表本项目负责生成这些上游文件。
- “源日期”“订单日期”“销售日期”“执行日期”“快照标签日期”并不总是同一天，具体口径见各任务说明。
- 下文 `YYYY` 表示数据所属年份，例如 `jst_daily_sales_2026`；查询分区父表通常可以跨年度读取，不能把年度子表当成另一套独立业务来源。
- 本次仅整理说明，未执行导入、修复、备份或修改计划，也未重启前后端。

## 四、商品主流程的来源和关联表

`HedeImportProductsDaily` 实际入口为 `backend/scripts/sync_products_and_copywriting_daily.cmd`，不是一次简单的 Excel 导入。

```text
管家婆合并商品信息（当天尚未成功时补跑）
  → 商品档案同步
  → 图片路径刷新 + US3 增量同步
  → 近 5 天上新商品提示词补生成
  → 商品标签增量同步
  → 合并物价导入 + 档案成本校准
```

| 步骤 | 数据来源 | 目标 / 关联表 | 更新规则 |
| --- | --- | --- | --- |
| 管家婆原始资料 | B 中“男女鞋合并商品信息” | `gj_merged_product_info` | 同源日期去重并替换，保留其他日期；与 04:00 独立任务共用业务状态。 |
| 商品档案 | 最新一批 `gj_merged_product_info`，A 中档案工作簿，H1～H3 中组别 / 等级资料，颜色和尺码等主数据 | `cbanner_mens_products`、`cbanner_womens_products`、`yandou_products`、`eblan_products`、`smiley_products`；档案身份维护涉及 `product_archive_identities` | 按 SKU 同步，不全表清空；已有商品冲突更新限源或已有上新日期为当前年。名称、型号、供应商、颜色、年份、季节、尺码段等有保留已有值的规则；手工成本覆盖标记保留。NI 排除在此日常来源同步外。 |
| 图片 | 已配置共享图片目录、档案中的 `image_path` | 档案图片路径、US3 对象；本地 `backend/.us3_image_sync_manifest.json` | 默认不强制覆盖已有路径；按文件签名增量上传，未变化文件跳过。图片不是存入一张图片二进制数据库表，也不是上传到后端 8000 端口。 |

| 标签 | 当前商品属性、运营字段、上新日期及质量规则 | `product_tag_definitions`、`product_tag_assignments` | 增量处理当日变动、缺规则标签和需调整生命周期标签的商品；重算规则来源的关联，不清空全部手工标签。`product_style_entities` 是标签体系相关表，不是此每日增量函数的主要写入目标。 |
| 物价 / 成本 | B / 日期目录 / 名称同时包含“合并”“物价”的 Excel；检查近 7 天 | `jst_product_price`；再校准内置品牌档案 `cost` | 原始物价按源日期替换并保留其他日期。档案成本采用最新合并男女鞋物价的“预设售价”，有 `cost_manual_override` 的商品跳过，不在此任务里重算历史单据单价。 |

主流程为分步提交，**不是跨这些表的一次总事务**。前面已成功的步骤不会因后面失败而整体撤销；当天重试跳过已成功步骤。图片失败会阻止后续提示词；提示词失败会阻止后续标签和物价步骤。主流程本身有数据库会话锁防止重入，并在跨业务日时停止继续处理。

### 品牌范围不能混为一谈

- 商品档案日常来源同步：当前内置千百度男女鞋、烟斗、伊伴、笑脸；NI 受保护，不由此来源覆盖。
- 图片路径刷新默认遍历 `domain.sources.TABLE_NAMES` 的四品牌：千百度男女鞋、烟斗、伊伴。US3 上传扫描可使用已注册档案品牌和已存在图片路径；这不代表所有新增品牌都已有独立共享图片匹配规则。
- 货品表计算快照、精细表快照及每日精细表导出：默认也是上述四品牌。
- 历史货品“商品明细表”回填、每日“订单数据”导入：默认仅千百度男女鞋、伊伴。
- 提示词和标签步骤按商品仓储层已注册档案品牌遍历，可包含手工新增品牌；但**新增品牌不会因此自动增加所有 Excel 导入、快照或导出计划**。
- 手工新增品牌的档案表由品牌配置 `product_table_name` 指定（如 `manual_product_archive_<编号>`）；不要将这些表误认作管家婆主流程自动生成的对应品牌数据。

## 五、容易混淆的表与更新口径

### 5.1 三类聚水潭库存任务

两张历史库存快照使用按键新增 / 更新；重新导入同一天并不等于先删除该天所有旧键。10:00 任务的三个导入步骤分别执行，某一步失败时应查看各步导入条数，不能假定所有表都已回滚。

### 5.2 唯品运营报表与唯品日销不是同一条链路

10:30 运营任务要求 D1、D2 的当日目录均具备八类报表：`3环比`、`3罗盘`、`7环比`、`7罗盘`、`实时商品`、`常态商品运营`、`日罗盘`、`月罗盘`。源目录齐全后才开始导入。

| 表 | 内容 | 更新与日期口径 |
| --- | --- | --- |
| `vip_product_daily` | 3 / 7 日环比，日 / 3 日 / 7 日 / 月罗盘等运营指标 | 首个源目录按报表类型和周期替换当前数据，后续目录按报表业务键合并。不能当作所有历史日报的完整累计表。 |
| `vip_product_daily_snapshots` | 日罗盘历史快照 | **仅“罗盘 + 1d”**生成；按 `snapshot_date + goods_id` 新增 / 更新。日期优先使用报表结束日期，解析不到时用源目录日期，仍取不到则用文件修改日期。不为所有周期各存一份每日快照。 |
| `vip_product_realtime` | 最近导入的实时商品信息 | 按 `goods_id` 新增 / 更新，不按日留历史；导入未出现的旧商品不会自动全部清除。“实时”是报表名称，不是本项目实时直连唯品平台。 |
| `vip_product_ops` | 最新常态商品运营信息 | 首目录替换、后目录合并，为当前态。 |

| `vip_daily_sales_YYYY` | 按销售日期、商品 ID、尺码 ID 的原始日销事实 | **09:30 的唯品日销任务**读取 E 中独立报表，按 `sales_date + goods_id + size_id` 新增 / 更新，历史保留。 |

因此，看到 `vip_product_daily_snapshots` 某些日期缺失，不能仅据此判断 `vip_daily_sales_YYYY` 也缺同一天；应分别查来源文件、业务日期和对应任务。周报也把唯品商品日快照列为非严格逐日采集项。

### 5.3 订单、日销、历史货品订单的区别

| 表 | 数据粒度 / 用途 | 保留规则 |
| --- | --- | --- |
| `jst_monthly_orders` | 聚水潭订单明细，来自近 3 月滚动导出 | 仅替换本次源文件订单日期最小值至最大值覆盖的窗口，保留窗口外数据；同时清理同源工作簿无日期旧行。相同订单业务标识却业务内容冲突时会拒绝写入，不能静默覆盖。 |

### 5.4 快照的真实含义

- **03:00 历史回填**：读取共享历史 Excel 的“商品明细表”，按文件名及目录推断业务日期，保留来源工作簿 / 行号；默认无固定最近 N 天限制，已有成功日期跳过。该脚本会补 `product_goods_overrides` 中空的所属平台、四级分类、角色、类型、抖音爆款、清仓、备注，不覆盖已有非空值。
- **20:00 货品计算快照**：从运行时的商品档案 / 管家婆资料、日销、库存、售后、历史货品数据和人工运营字段计算结果，再写入昨天日期；不是再次读取历史 Excel。同品牌同日期会替换，因此可能覆盖回填得到的同日快照。
- **21:00 精细表快照**：从运行时档案 / 管家婆、唯品运营、聚水潭库存 / 订单等数据库数据计算；批次在 `fine_table_snapshot_batches`，日期行引用在 `fine_table_snapshot_refs_YYYY`，不变内容和指标分别去重存入 `fine_table_snapshot_payloads`、`fine_table_snapshot_metrics`，并更新筛选缓存。
- `fine_table_snapshot_rows_YYYY` 是兼容旧版整行快照的表；当前新快照主要走引用和去重内容结构，不能只查旧行表判断有无快照。
- **22:00 导出**默认处理当天快照，已存在时复用，缺失时创建，输出四品牌 Excel；与 21:00 的昨日快照日期不同。
- `--previous-day` 只是快照标签日期。当前 20:00 / 21:00 入口并未按昨日某一时点完整重放所有上游数据，不能据此承诺它们就是“昨日日终原样数据”。
- 笑脸独立使用 `smiley_fine_table` 按日期存储分析结果；导入时默认清理同日旧 `xiaolian` 品牌的兼容精细表快照，不是向四品牌精细表任务自动增加笑脸。

### 7.1 两张状态表不是一回事

| 表 | 用途 |
| --- | --- |
| `scheduled_task_runs` | 统一运行器记录实际启动的一次进程：任务名、开始 / 结束、退出码、日志路径、错误摘要等。Windows 触发后若在包装器中发现当天已成功，会直接写文件日志并返回，不一定新增运行行；数据库不可用时也可能只留下文件日志。 |
| `scheduled_task_statuses` | 支持业务状态的任务按 `task_name + business_date` 保存处理状态、源路径、结果和尝试次数，供幂等跳过 / 重试使用；不是每次进程运行各一行。 |
| `inventory_import_tasks` | 用户在经营历程等入口提交的后台模板导入任务，**不是 Windows 所有定时任务的总表**。 |

常用业务状态名：

| 任务或步骤 | `scheduled_task_statuses.task_name` | `business_date` 口径 |
| --- | --- | --- |
| 商品主流程 | `sync_products_and_copywriting_daily` | 执行当天 |
| 商品档案 / 图片 / 提示词 / 标签 | `sync_products_daily` / `refresh_product_images_daily` / `generate_product_copywriting_daily` / `sync_product_tags_daily` | 执行当天 |
| 管家婆 / 物价 | `import_gj_merged_product_info_daily` / `import_price_daily` | 所处理源目录日期，可能是近 7 天中的历史日 |
| 月订单 / 售后 / 得物 | `import_monthly_order_daily` / `import_aftersale_returns_daily` / `import_dewu_orders_daily` | 执行当天；不等于源窗口中全部订单都发生在当天 |
| 每日可用库存 / 库存明细 | `sync_jst_stock_daily` / `import_jst_daily` | 传入业务日，默认当天 |
| 唯品运营 | `import_vip_product_daily` | 源目录业务日，默认当天；日罗盘快照日期另按报表解释 |

| 货品历史订单 | `import_product_goods_orders_<品牌编码>` | 工作簿内最大订单日期 |
| 维护 | `database_maintenance` | 执行当天 |

售后实际 Windows 动作虽然带 `--force`，但外层统一运行器仍有“当天业务成功则跳过”的检查。因此此参数并不保证手动再次触发同一个 Windows 任务后一定重新导入。

### 7.2 只读排查示例

```sql
SELECT task_name, status,
       started_at AT TIME ZONE 'Asia/Shanghai' AS started_at_beijing,
       finished_at AT TIME ZONE 'Asia/Shanghai' AS finished_at_beijing,
       exit_code, log_path, error_summary
FROM scheduled_task_runs
ORDER BY started_at DESC
LIMIT 100;

SELECT task_name, business_date, status, source_path, message,
       finished_at AT TIME ZONE 'Asia/Shanghai' AS finished_at_beijing
FROM scheduled_task_statuses
WHERE business_date >= (CURRENT_TIMESTAMP AT TIME ZONE 'Asia/Shanghai')::date - 7
ORDER BY business_date DESC, task_name;
```

判断“今天有没有更新”时，先定位对应任务，再核对状态、实际源路径、源文件日期和目标表业务日期，最后查看完整文件日志。不要仅凭 Windows 显示“就绪”、历史运行成功或表里有数据就判断今天已成功。

## 八、运行条件与边界

- 这些项目任务通过独立 Python 进程直连 PostgreSQL，**不需要前端或 FastAPI HTTP 服务持续运行**；即使复用了 API 路由中的计算函数，也是在脚本进程内调用，不是向 8000 端口发请求。
- 关掉后端服务通常不妨碍已经独立运行的计划脚本；但关闭服务器、杀死任务进程、数据库停止、共享目录不可达都会影响它。网页后台模板导入是另一种运行方式，不能与 Windows 独立计划混淆。
- 当前只有关联检查任务使用 `SYSTEM / ServiceAccount`；其他本次核对任务均为 `Administrator / Interactive`，依赖该账号登录会话。共享文件访问权限也与运行账号有关。
- 每日快照不是数据库完整备份。已核对的这 25 项计划中**没有定时完整数据库备份任务**；本说明不据此判断服务器其他名称任务或项目外备份工具是否存在。
- 缺失巡检不会自动补销量，关联检查不会自动修复关联，索引巡检不会自动删索引，冷热巡检不会自动删除历史数据。
- 定时计划成功不保证网页立即刷新：还需考虑派生汇总、数据日期、品牌范围以及页面 / 后端查询缓存。
