# 订单历史冷热归档方案

## 目标

`jst_monthly_orders`、`jst_aftersale_returns`、`dewu_orders` 使用两级在线存储：

- 热层：当前年度和上一年度，存放于 PostgreSQL 默认高性能表空间。
- 冷层：更早且已经结束的年度，存放于独立物理磁盘上的冷表空间。

冷分区仍挂在原父表下，因此页面、API 和 SQL 表名不变。带日期条件的查询由
PostgreSQL 自动裁剪到相应冷热分区。

## 安全规则

1. 当前年度、下一年度和 `default` 分区始终为热数据。
2. 默认保留当前年度和上一年度为热数据，避免跨年滚动窗口修改冷分区。
3. 冷分区增加数据库触发器，禁止 `INSERT`、`UPDATE`、`DELETE` 和 `TRUNCATE`。
4. 移动分区时同时移动该分区的全部索引。
5. 冷表空间必须位于 PostgreSQL 数据目录之外。
6. 冷磁盘必须是独立物理磁盘；同一硬盘的不同盘符不视为真正冷存储。
7. 冷迁移不会自动删除数据，也不会改变父表和分区关系。
8. 每个分区迁移前获取独占锁，并校验迁移前后行数；锁等待超过 30 秒则退出重试，
   不在繁忙时段强行迁移。

## 当前环境结论

PostgreSQL 数据目录位于 `D:\Postgresql\data`。`D:` 与 `E:` 都位于同一块
Kingston NVMe 物理磁盘。当前已按管理决定允许使用 `E:`，因此可以获得不同卷、
不同表空间及历史只读保护带来的逻辑冷热分层，但不能获得独立磁盘的 I/O 隔离和
故障隔离。后续增加独立硬盘后，可用同一迁回机制再次移动冷分区。

系统默认仍拒绝同物理盘。只有明确设置
`ORDER_HISTORY_ALLOW_SAME_PHYSICAL_DEVICE=true` 后才允许使用 `E:`，并在预览报告
中标记 `same_physical_device=true`，避免把逻辑分层误认为独立磁盘冷热分层。

按 2026-09-13、保留两个热年度计算：

- `jst_monthly_orders_2024` 应进入冷层，约 10 GB。
- `jst_aftersale_returns_2024` 应进入冷层，约 1.4 GB。
- `dewu_orders` 暂无需要进入冷层的年度，最早数据在 2025 年。
- 2025、2026、2027 和 `default` 分区保留在热层。

## 首次配置

当前冷层使用 `E:`：

1. 创建空目录 `E:\Postgresql\cold_archive`。
2. 将该目录的完全控制权限授予 PostgreSQL 服务账户
   `NT AUTHORITY\NetworkService`。
3. 在数据库执行：

```sql
CREATE TABLESPACE hede_cold_archive
LOCATION 'E:\Postgresql\cold_archive';
```

4. 在 `backend/.env` 增加：

```dotenv
ORDER_HISTORY_COLD_TABLESPACE=hede_cold_archive
ORDER_HISTORY_COLD_LOCATION=E:\Postgresql\cold_archive
ORDER_HISTORY_HOT_TABLESPACE=pg_default
ORDER_HISTORY_KEEP_HOT_YEARS=2
ORDER_HISTORY_ALLOW_SAME_PHYSICAL_DEVICE=true
```

## 执行方式

先只读预览：

```powershell
cd E:\hede\backend
.venv\Scripts\python.exe -m scripts.manage_order_history_tiers
```

确认后执行迁移：

```powershell
.venv\Scripts\python.exe -m scripts.manage_order_history_tiers --apply
```

`scripts\manage_order_history_tiers.cmd` 是供 Windows 计划任务使用的正式迁移入口，
默认带 `--apply`。任务可按月运行；已在目标表空间且只读保护正确的分区会跳过，
不会重复搬迁、锁表或统计整张历史分区。

把指定分区迁回热层：

```powershell
.venv\Scripts\python.exe -m scripts.manage_order_history_tiers `
  --apply --restore-hot --partition jst_monthly_orders_2024
```

移动分区需要短暂独占锁，建议在无导入、无大查询的维护窗口执行。首次迁移约
11.4 GB，耗时取决于冷磁盘写入速度。

执行前会校验冷盘剩余容量。剩余空间必须至少覆盖“待迁移分区总大小 + 安全余量”，
安全余量取 5 GB 与迁移量 15% 中的较大值。按当前约 11.4 GB 的迁移量计算，首次
迁移至少需要约 16.4 GB 可用空间；实际选盘还应为后续年度增长保留充足容量。

独立冷盘和表空间配置完成后，建议将 `HedeOrderHistoryTiering` 注册为每月 15 日
凌晨 02:00 执行。当前机器尚未注册该计划任务，避免在冷盘未就绪时持续产生失败记录。

## 查询影响

- 热数据查询不变。
- 历史数据仍可直接查询原表，不需要手工恢复。
- 冷年度查询速度取决于冷磁盘，通常慢于热层。
- 不带日期条件的全表查询会同时访问冷热层，应尽量提供日期范围。
- 独立磁盘损坏时冷年度查询不可用，因此冷表空间不能替代数据库备份。

## 离线备份

在线冷表空间解决容量和 I/O 分层，不解决误删、勒索软件和整机故障。冷分区还
应使用 `pg_dump` 或数据库备份工具生成加密副本，并上传到专用私有对象存储。
现有 `hede-img` 是图片用途的存储桶，不应混放数据库归档；需要单独创建私有桶、
最小权限密钥、版本控制和保留策略，并定期做恢复演练。
