# “存”板块：库存预警

更新日期：2026-11-14。

## 页面与默认规则

左侧菜单“存”包含两个预警页面及新增的[补货建议](补货建议.md)，查询条件及页码分别保留。

| 页面 | 地址 | 默认预警条件 |
|---|---|---|
| 新品零动销预警 | `/stock-alerts/new-products` | 上市满 15 天、有正可售库存，上市后销售数量为 0 |
| 低售罄、滞销预警 | `/stock-alerts/slow-sales` | 上市满 60 天、有正可售库存，参考售罄率低于 20% |

参考售罄率＝上市后净销量 ÷ 历史正向采购入库量 × 100%。历史正向采购入库包含补货，采购退货数量尚不完整，因此该值用于筛选跟进对象，不能视为准确的批次售罄率。

新品零动销使用销售数量判定。已经销售、随后全部退回而使净销量变成 0 的商品，不算从未销售。低售罄按未舍入的比率比较阈值；显示值保留两位小数，恰好等于阈值不预警。

“上市时间”取商品信息档案，不是平台上架时间；平台上架时间尚未接入。上市天数为日销截止日减上市日期，不以打开页面的当天计算。采购首入、最近入库日期仅作参考，不代表现存实物的准确库龄。

## 查询与规则设置

选择品牌、季节，或输入货号、原始货号、品名、颜色，点击“查询”应用条件。输入中的草稿不改变当前清单、统计或规则设置范围。

- “待跟进商品”是全部匹配商品中的预警项数，不是当前页行数。
- “预警可售库存”只合计待跟进商品的可售库存，不包含待核对商品。
- 点击“数据待核对”查看缺少上市日期、日销覆盖或有效采购入库参考量等原因；不将缺失数据当作销量 0。
- 列表按可售库存降序展示，每页 25 项；统计在分页前完成。
- “刷新”立即重新查询现有来源，不触发来源同步或渠道日汇总重建。

有 `product.manage` 权限的用户可点击“设置规则”，修改上市天数及低售罄阈值。上市天数范围 1–3650 天，阈值范围 0–100%。

规则范围取**已经查询的品牌和季节**，不是尚未提交的输入。选择“全部季节”保存品牌通用规则；选择具体季节保存季节专属规则。两个预警类型分别保存，优先级为：

`商品所属季节的专属规则 → 品牌通用规则 → 默认规则`

查询全部季节时，逐个商品按其所属季节确定规则，不统一套用页面显示的品牌通用值。规则保存后对所有有查看权限的账户共享。并发修改同一范围时检查版本，旧版本保存返回 409，页面保留草稿并提示关闭设置、刷新后重试。

查看菜单和读取接口使用 `product.view`，保存规则使用 `product.manage`；权限在服务端同样检查。成功保存写操作日志，并通知同一浏览器、同一站点的其他标签页重新查询，不包含跨设备实时推送。

## 数据来源及匹配

| 内容 | 数据源与口径 |
|---|---|
| 商品资料 | 品牌商品信息档案中的货号、原始货号、颜色、尺码组、条码构成逻辑、上市时间、年份和季节；排除已删除商品 |
| 可售库存 | `jst_full_stock` 最新 `sync_date` 快照的 `available_qty`，按唯一匹配的商品汇总，只纳入合计大于 0 的商品 |
| 采购参考 | `mv_jst_purchase_inbound_age_reference` 的 `first_inbound_date`、`last_inbound_date`、`received_quantity` |
| 销量 | `factory_channel_sales_daily_summaries` 中当前品牌已匹配商品的上市日至截止日汇总：销售数量、退回数量及净销量 |
| 日销覆盖 | 核对 `jst_daily_sales`、`vip_daily_sales` 和渠道日汇总的品牌 `date_marker`，逐日检查上市日至截止日是否完整 |
| 共享规则 | `stock_alert_rules`，按品牌、季节、预警类型保存 |

日销截止日取**北京时间业务昨日、聚水潭日销最新日期、唯品日销最新日期三者中的最早日期**。任一日销来源完全无数据时不判定预警。库存及日销日期在页面明确展示，来源落后时给出提示。

库存和采购编码匹配先检查准确货号、原始货号及条码基础编码，再使用商品条码构成规则和实际尺码条码解析。跨品牌或颜色存在歧义时不选取任一候选，无法唯一匹配的库存编码组在来源说明中显示数量，不纳入预警。

渠道日汇总复用已有聚水潭、唯品日销计算结果，唯品同商品同日按既有规则去重；唯品日销未单列退货。新增商品或修改货号后，历史销售识别需要等待既有渠道日汇总重新生成，本页刷新不会补算这些历史记录。动态品牌未生成渠道日汇总时，相关商品进入数据待核对。

上市日期缺失或无效、上市日晚于日销截止日、任一日销或品牌汇总日期有缺口时，商品进入待核对。低售罄另需有效采购入库参考量；最近入库晚于日销截止日时，等待数据对齐。这两项采购资料问题不阻止资料完整的新品零动销判定。

## 运行与维护

后端仍由负责人手动启动。新代码在下一次人工启动时通过 `create_app` 检查并创建 `stock_alert_rules` 小型配置表；本次未在正式库执行建表，也未启停服务。该表只存规则、版本、操作者及更新时间，不回写商品、库存或单据。没有新增定时任务，也不自动发送提醒消息。

首次查询读取已有物化采购汇总和渠道日汇总，使用只读、可重复读事务，单条 SQL 超时 25 秒。不能改为在原始采购明细上执行跨多个编码字段的大范围聚合。

事实缓存按数据库引擎、品牌和北京时间业务日期隔离，最长 120 秒，最多 4 项、总计 8 MiB；构建锁限制并发构建，避免重复查询放大内存。规则每次重新读取，修改规则复用事实缓存；手动刷新及收到商品、库存变更通知时绕过事实缓存。HTTP 响应使用 `Cache-Control: no-store`。

实现入口：

- 菜单：[navigation.ts](../frontend/lib/navigation.ts)。
- 页面与规则弹窗：[stock-alerts](../frontend/components/stock-alerts/)。
- 接口：[stock_alerts.py](../backend/api/routes/stock_alerts.py)：`GET /stock-alerts/options`、`GET /stock-alerts`、`PUT /stock-alerts/rules`。
- 判定与匹配：[domain/stock_alerts.py](../backend/domain/stock_alerts.py)。
- 来源查询与缓存：[stock_alert_facts.py](../backend/storage/stock_alert_facts.py)。
- 规则持久化：[stock_alert_rules.py](../backend/storage/stock_alert_rules.py)。

`/stock-alerts` 和旧 `/product-inventory-alerts` 地址均跳转新品零动销页面，不保留旧商品库存预警菜单。

## 复验要点

前端行为回归入口为 [stock-alerts-page.test.tsx](../frontend/components/stock-alerts/stock-alerts-page.test.tsx)，菜单和跨标签页通知沿用现有对应测试。后端临时验证仅保存在本机 `outputs/logs/`，不上传 `backend/tests/`，不以正式业务数据运行写入测试。

修改计算口径时，至少复验上市 15/60 天边界、售罄率等于阈值、销售后全退回、日销缺日、采购量缺失、跨品牌条码歧义、季节规则继承、全部季节统计与分页、并发保存冲突及只读账户拒绝写入。
